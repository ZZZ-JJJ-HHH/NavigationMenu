## 📌 一句话核心

> <span style="color:red">**self-hosted runner = 把 Jenkins Agent 那套搬到 GitHub：你自己的机器注册上去领任务，构建和部署都在它上面跑。**</span>

---

## 🎯 背景与问题

### GitHub 托管 runner 的四个限制

`runs-on: ubuntu-latest` 用的是 GitHub 提供的机器。它够用，但有四条绕不开：

| 限制 | 表现 |
|------|------|
| 每次都是全新空机器 | 上一轮的 MySQL、依赖、缓存一点不留，`ci.yml` 里必须现起服务、现下依赖 |
| 私有仓库有免费分钟上限 | 公开仓库不限制，私有仓库用超了要付费 |
| 进不了你的内网 | 连不到公司数据库、内网服务、内网镜像仓库 |
| 规格固定 | 想要 GPU、大内存、特定操作系统版本，没得选 |

### 核心痛点

> ⚠️ **第一条才是真正的痛点**。CI 的价值是"每次都能跑"，但如果每次都要花几分钟重装环境和重下依赖，跑得越勤越难受。托管 runner 的清爽，是用"每次都从零开始"换来的。

---

## 💡 核心目的

**用你自己的机器换掉 GitHub 的一次性沙箱，换取四样东西：**

1. **成本不封顶**——机器是你的，跑多少次都不额外花钱
2. **环境常驻**——依赖预装好，第一次下载之后都在本地，后续任务启动快
3. **能进内网**——runner 坐在你的网络里，访问内网服务不需要打洞
4. **规格自定**——硬件、操作系统、预装软件全部你自己说了算

代价是：机器得你维护，而且**安全性从一个"用完即弃的沙箱"退化成了"你自己的真实电脑"**。这一条后面会重点讲。

## ⚙️ 原理与机制

### 连接方向：由内向外

这是最容易误解的地方。**不是 GitHub 连进你的电脑，是你的电脑连出去找 GitHub 要活干。**

```java
你的电脑                                GitHub
   │                                      │
   │  run.cmd 启动，一个常驻进程            │
   │  ──── 主动连出去，问「有活吗」───────▶ │
   │  ◀─── 「有，这是任务详情」───────────│
   │                                      │
   │  在本地起进程，执行任务里的命令          │
   │  ──── 回报日志和结果 ───────────────▶ │
```

因为是 outbound，所以**不需要公网 IP、不用在路由器上开端口、不用改防火墙**。这也是它和"远程桌面"最表面的区别。

> ⚠️ **但这不代表它更安全**。连接方向只决定"谁先发起连接"，不改变权限。任务内容是 GitHub 上那份 workflow 文件写的，执行时是在**你的机器上、以你启动 runner 的那个用户身份**跑的。
>
> 所以真实结论是：你没有把电脑的控制权交给 GitHub，但你交给它一个**自动执行远程指令的常驻入口**。

### 任务是怎么落到这台机器上的

```java
开发者 git push
      │
      ▼
GitHub 读取 .github/workflows/ci.yml
      │
      ▼
每个 job 的 runs-on 决定它落到哪
      │
      ├── runs-on: ubuntu-latest   ──▶ GitHub 提供的临时沙箱
      │                                  （跑完即销毁，什么都不留）
      │
      └── runs-on: self-hosted     ──▶ 你注册上去的那台机器
                                         （跑完还在，痕迹也还在）
```

`runs-on` 是唯一的开关。一个 workflow 里可以混用：测试跑在托管 runner 上，部署跑在自托管 runner 上。

### 注册流程（Windows）

1. 仓库 **Settings → Actions → Runners → New self-hosted runner**，选 Windows
2. 页面会给出几条命令：下载 runner 压缩包、解压、执行 `config.cmd` 完成注册
3. `run.cmd` 前台启动，或者注册成 Windows 服务让它开机自启
4. workflow 里把 `runs-on` 改成 `self-hosted`

> 🔑 **注册动作本身就说明了一切**：登记是在你自己的机器上主动完成的，GitHub 全程没有连进来过。

## 📊 应用与对比

### 两种 runner 横向对比

| 维度 | GitHub 托管 runner | self-hosted runner |
|------|-------------------|-------------------|
| 机器归谁 | GitHub | 你自己 |
| 费用 | 公开仓库免费，私有仓库有分钟上限 | 免费（电费自付） |
| 环境 | 每次全新 | 常驻，上次的痕迹还在 |
| 启动速度 | 慢，要重装环境、重下依赖 | 快，依赖已在本地 |
| 内网访问 | ❌ 不行 | ✅ 行 |
| 硬件规格 | 固定套餐 | 自定 |
| 维护成本 | 零 | 系统更新、清理、补丁全归你 |
| 机器必须开机 | 不需要 | 需要，关了就排队 |
| **被恶意任务执行后** | **沙箱销毁，无影响** | **你的电脑被入侵** |

### 与 Jenkins Agent 的对应关系

这套东西对用过 Jenkins 的人来说就是旧识：

| GitHub Actions | Jenkins | 说明 |
|----------------|---------|------|
| `runs-on: ubuntu-latest` | 云端 Jenkins 自带的构建节点 | 别人提供的机器 |
| `runs-on: self-hosted` | Jenkins Agent / Node | 你自己的机器，注册上去领任务 |
| runner 注册 | agent 注册（JNLP / SSH） | 都是"机器主动向外登记" |
| workflow 文件 | Jenkinsfile | 任务的定义 |

两者连通信方向都一样：agent 主动向外连，不需要 master 能连进来。

### 安全风险：公开仓库的完整攻击链

这是自托管 runner 最大的坑，也是 GitHub 官方文档专门警告的点。

```java
① 你的仓库是公开的
      │
      ▼
② 陌生人 fork，改掉 .github/workflows/ci.yml，提一个 PR
      │
      ▼
③ on: pull_request 触发工作流
      │
      ▼
④ runs-on: self-hosted → 任务被派到你的电脑
      │
      ▼
⑤ PR 里的命令，以「你启动 runner 的那个用户身份」执行
      │
      ▼
⑥ 读环境变量 / 翻你的文件 / 装后门 / 拿去挖矿
```

关键在于**第 ④ 步把沙箱换成了你的真实电脑**。同一份恶意 PR，跑在托管 runner 上，最坏结果是那台一次性机器被玩坏，销毁就完事；跑在自托管 runner 上，就是你的机器被入侵。

### 缓解措施

| 措施 | 效果 |
|------|------|
| 仓库转私有 | 最有效的一刀，直接掐断"陌生人能提 PR"这条路 |
| 用 runner group 限制可派发的工作流 | 缩小能被触发的范围 |
| 收紧 fork PR 的审批开关 | 让外部 PR 必须先经人工批准才跑 |
| runner 不用管理员账户 | 降低被利用后的权限 |
| 机器上不放敏感凭据 | 降低被利用后的收益 |
| 跑在隔离的虚拟机 / 容器里 | 把"你的电脑"重新变成沙箱，最彻底 |

> **fork PR 审批开关**在仓库 Settings → Actions → General 的 "Fork pull request workflows" 一节。本项目实测的默认值是 `first_time_contributors`——只有**首次**贡献者的 fork PR 才需要批准，已经有过贡献记录的人开 PR，工作流会直接跑。现已改为 `all_external_contributors`。

### 本项目当前状态：一个已知并暂时接受的风险

本项目**已经**在公开仓库上注册了 runner（`zhan-pc`，标签 `navigation-menu-deploy`）。这是一个清楚的已知风险，暂时接受、待处理，因此专门记录在这里，避免被忘掉。

**为什么现有的缓解措施不够**

直觉上 `deploy` job 上的这条限制应该够用：

```yaml
if: github.event_name == 'push' && github.ref == 'refs/heads/main'
```

理由是：fork 提的是 pull_request 事件，落不到 deploy job 上。但这条推理只覆盖了**我们自己写的那个 job**。攻击者根本不需要动它——他可以在自己的 fork 里**新写一个 workflow**，直接点名你的 runner：

```yaml
# 攻击者 fork 里的任意一个新 workflow 文件
on: pull_request
jobs:
  pwn:
    runs-on: [self-hosted, navigation-menu-deploy]
    steps:
      - run: echo "以维护者的身份，在维护者的电脑上执行"
```

然后开一个 PR。官方文档那句 "any user can open pull requests against the repository and compromise the environment" 说的正是这个。

**与托管 runner 的本质差别在于能否持久化。** 托管 runner 每次是干净的一次性虚拟机，被玩坏也只是那台机器销毁；自托管 runner 在你自己的电脑上，官方原话是 "can be persistently compromised"——写注册表启动项、改 PATH、留后门，任务结束之后全都还在。

**当前实际生效的防护**

| 措施 | 状态 |
|------|------|
| fork PR 工作流审批 | 已从 `first_time_contributors` 收紧为 `all_external_contributors` |
| runner 自定义标签 | `navigation-menu-deploy`，收窄任务派发范围 |
| deploy 触发条件 | 仅 `push` 到 `main` |
| 仓库级 GITHUB_TOKEN 默认权限 | `read` |
| 仓库可见性 | **公开** ← 风险源头未消除 |

审批收紧把门从"虚掩"改成了"要你亲手开"，但**没有消除风险**——你仍然可能被一个看起来正常的 PR 骗着点了批准。

**两条退出路径（待执行）**

**路线 A：仓库转私有**

```bash
gh repo edit ZZZ-JJJ-HHH/NavigationMenu --visibility private
```

直接消除"陌生人能提 PR"这个来源。个人私有仓库没有协作者，能开 PR 的只有你自己。代价是不能作为公开作品展示——这与 `docs/项目规划/简历.md` 的用途直接冲突，也正是这个项目一直没有转私有的原因。

成本上不必顾虑：私有仓库的 CI 消耗免费额度（Free 账号 2000 分钟/月），但 self-hosted runner 的耗时**不计费**；本项目每次 push 约 1.3 分钟托管 runner 时间，一个月能跑上千次。而且可逆，改回 `public` 即可。

**路线 B：保持公开，去掉 runner**

把 `deploy` job 换成本机定时拉取，风险面直接归零——没有 runner，就没有任何远端任务能在你机器上执行。落地有四个约束：

| 约束 | 原因 |
|------|------|
| 只能 pull `app` 一个服务 | 无差别 pull 会连带更新 `mysql:8.0` / `redis:7` 这类移动 tag。实测中 `docker compose pull redis` 就把本地 `redis:7` 换成了新版本，下一次 `up -d` 会顺手重建数据库容器 |
| 加 `--no-build` | `app` 服务同时有 `build:` 和 `image:`，不加这个参数它可能尝试本地构建 |
| 监控的 tag 必须会移动 | 轮询的机器猜不出最新的 commit SHA 是哪个，所以得改用 `latest` |
| 拉取失败不能中断循环 | 轮询不知道 CI 是否还在构建中，撞上构建中途会失败 |

时效性上不必担心：现在这条"即时"链路本身就要约三分半（test 46s + image 36s + deploy 1m55s），轮询只是在上面再加"最多一个间隔"。间隔取 2 分钟的话，最坏总延迟约五分半，演示场景基本无感。

改用 `latest` 会丢一部分可追溯性，两条补偿路线：一是拉取后记录 digest，需要时再从 provenance 里取 `vcs:revision`；二是让轮询脚本先问 GitHub API "main 上最近一次成功的运行是哪个 SHA"，再拉那个 SHA——可追溯性完整保留，代价是未认证的公开 API 每小时只有 60 次配额，间隔至少要 2 分钟。

### 什么时候该用，什么时候不该用

**该用**：私有项目想省分钟数或让环境常驻；构建需要访问内网资源；需要特殊硬件或操作系统版本。

**不该用**：公开仓库；只是想跑跑测试；团队里没人愿意承担机器维护；追求"配置越少越好"。

## 🔥 面试要点

### 高频问题 + 标准答案

> **Q1：self-hosted runner 是什么？和 GitHub 托管 runner 有什么区别？**
>
> 自托管 runner 是你自己的一台机器，注册到 GitHub 上领任务执行，相当于把 Jenkins Agent 那套搬了过来。
>
> 区别有四点：托管 runner 每次是全新沙箱、私有仓库有免费分钟上限、进不了你的内网、规格固定；自托管环境常驻、用自己的机器所以免费、能访问内网、规格自选。代价是要自己维护，而且有安全风险。

> **Q2：自托管 runner 不需要公网 IP，是不是说明它更安全？**
>
> 不是。不需要公网 IP 只是因为连接方向是 outbound——runner 主动连 GitHub 长轮询领任务，不需要外部连进来，所以不用开端口、不用改路由器。
>
> 但这只决定"谁先发起连接"，不改变权限。任务内容来自 GitHub 上的 workflow 文件，执行时是在你的机器上、以你的用户身份跑。**谁能改 workflow 文件，谁就能在你的机器上执行命令。** 方向和安全是两件事。

> **Q3：自托管 runner 有什么风险？怎么缓解？**
>
> 核心风险在公开仓库：任何人 fork 之后改掉 workflow 文件提 PR，就能在维护者的机器上执行任意命令——因为 GitHub 的一次性沙箱被换成了维护者的真实电脑。
>
> 缓解手段：仓库转私有；用 runner group 限制可派发的工作流；收紧 fork PR 的审批开关；不给 runner 管理员权限，用专用低权限账户；机器上不放敏感凭据；更彻底的做法是把 runner 跑在隔离的虚拟机或容器里。
>
> 一句话原则：**公开仓库不要用自托管 runner。**

> **Q4：什么情况下你会选择自托管 runner？**
>
> 三种：私有项目想省分钟数或让环境常驻；构建需要访问内网资源；需要特殊硬件（比如 GPU）或不能接受每次重装环境。
>
> 反过来，公开仓库、只想跑测试、或者团队没人愿意维护机器，就用 GitHub 托管的。

### 关键词速记

| 关键词 | 一句话 |
|--------|--------|
| outbound | runner 主动连 GitHub，所以不需要公网 IP |
| runs-on | 唯一的开关，决定任务落到托管还是自托管机器 |
| 环境常驻 | 自托管的收益，也是它的隐患（上一轮的痕迹还在） |
| 公开仓库 + 自托管 | 不该出现的组合 |

```java
      │                                + buildx 构建镜像        （CI，已实现）
      │
      └── runs-on: self-hosted    ──▶ docker compose pull && up -d
                                             │
                                             ▼
                                        服务在本机跑起来      （CD，已实现）
                                             │
                                             ▼
                               Cloudflare Tunnel 暴露到公网（内网穿透，待实现）
```

### 三种"在哪执行"的方案对比

| 方案 | 需要什么 | 适合谁 |
|------|---------|--------|
| GitHub 托管 runner | 什么都不用 | 公开仓库、开源项目、只想跑 CI |
| self-hosted runner | 一台常开的机器 + 维护意愿 | 私有项目、要访问内网、要落地部署 |
| 云服务器 + SSH 部署 | 一台云主机 + 公网 IP | 需要真实公网服务、能接受付费 |

> 🔑 **自托管 runner 解决的是"在哪儿执行"，不解决"外部怎么访问"**。它能让部署命令落在你本机跑，但想让别人从公网打开你的应用，还得靠内网穿透。这两件事必须分开办，混在一起想就会卡住。

### 正确的决策顺序，以及本项目实际走成了什么样

**推荐顺序：**

```java
① 仓库是公开的吗？
      │
      ├── 是 ──▶ ② 先转私有（或把部署拆到私有仓库），再考虑 runner
      │
      └── 否 ──▶ ② 注册 runner，写 runs-on: self-hosted
                        │
                        ▼
                  ③ 写部署那一步：docker compose pull && up -d
```

**本项目实际走成了：**

```java
① 仓库是公开的
      │
      ▼
② 直接注册了 runner（zhan-pc）        ← 跳过了前置条件
      │
      ▼
③ 事后才发现这属于官方明确不建议的组合
      │
      ▼
④ 现状：保留 runner，风险已记录，待处理   ← 当前位置
```

**顺序反了，风险就落在你毫不知情的时候。** 自托管 runner 的价值在于把流水线从"别人的沙箱"搬回"自己的机器"，而它的全部风险也来自同一个动作。收益和代价是同一件事的两面，这才是需要先想清楚的地方。两条退出路径见上面「本项目当前状态」一节。
