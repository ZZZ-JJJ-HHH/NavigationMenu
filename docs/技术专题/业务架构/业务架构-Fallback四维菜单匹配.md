## 📌 一句话核心

> <span style="color:red">**先一次性全量匹配，再对同一 node_id 保留精确维度最多的一条。**</span>

---

## 🎯 背景与问题

菜单配置不能只按单一用户或单一分行写死，需要同时适配：

- 国家
- 业务实体
- 渠道
- 分行

同一条菜单可能既有全局默认版本，也有某个国家或分行的专属版本。

最初考虑使用经典 Fallback：从最精确条件开始查，不命中就逐级把维度改成 `*`。实际实现后发现查询次数多、合并和去重复杂，维度扩展也不方便。

---

## 💡 核心目的

用一次数据库查询完成：

1. 选出所有可能匹配的菜单记录
2. 对每条记录做四维通配匹配
3. 匹配上的记录按 `node_id` 去重
4. 同一节点保留精确值维度最多的版本

---

## ⚙️ 原理与机制

### 四个业务维度

| 维度 | 示例 | `*` 的含义 |
|:---|:---|:---|
| `country` | `CN`、`HK` | 任意国家 |
| `entity` | `RETAIL`、`CORPORATE` | 任意实体 |
| `channel` | `APP`、`PC` | 任意渠道 |
| `branch` | `SH001`、`BJ001` | 任意分行 |

匹配规则：

```text
配置值是 *        → 该维度匹配任意请求值
配置值是具体值    → 必须和请求值完全相等
```

### 全量匹配与精确优先去重

```java
1. SELECT 所有有效菜单配置
2. 对每条记录执行 wildcardMatch
3. 保留匹配成功的记录
4. 按 node_id 分组
5. 比较每条记录的精确值数量
6. 保留精确值最多的记录
```

精确值数量的计算不需要额外 `level` 字段：

```text
country=HK, entity=*, channel=*, branch=*  → 精确度 1
country=*,  entity=*, channel=*, branch=*  → 精确度 0
```

## 📊 应用与对比

### 方案演进

| 阶段 | 方案 | 问题 |
|:---|:---|:---|
| 1 | 经典 Fallback 逐级查询 | 多次 SQL、多个结果集、合并复杂 |
| 2 | 逐级查询 + level 标记去重 | 标记容易漏，维度扩展要改代码 |
| 3 | 全量查询 + 通配匹配 + 精确优先去重 | 一次查询，逻辑集中 |

### 真实数据示例

| id | node_id | 名称 | country | entity | channel | branch | parent_id |
|:---|:---|:---|:---|:---|:---|:---|:---|
| 1 | home | 首页 | `*` | `*` | `*` | `*` | 0 |
| 2 | account | 我的财富 | HK | `*` | `*` | `*` | 0 |
| 3 | account | 我的账户 | `*` | `*` | `*` | `*` | 0 |
| 4 | housing | 公积金 | CN | RETAIL | `*` | `*` | 0 |
| 5 | digital | 数字人民币 | CN | RETAIL | APP | SH001 | 3 |

### 三个验证场景

**HK 用户**

```text
请求：HK + RETAIL + PC + HK001
匹配：id=1 首页、id=2 我的财富、id=3 我的账户
去重：id=2 与 id=3 同为 node_id=account，保留更精确的 id=2
结果：首页、我的财富
```

**上海用户**

```text
请求：CN + RETAIL + APP + SH001
匹配：id=1 首页、id=3 我的账户、id=5 数字人民币
结果：首页、我的账户、数字人民币
```

**北京用户**

```text
请求：CN + RETAIL + APP + BJ001
id=5 的分行是 SH001，因此不匹配
结果：首页、我的账户
```

### 新旧方案对比

| 对比项 | 逐级 Fallback | 全量匹配 |
|:---|:---|:---|
| SQL 次数 | N 个维度等级 N 次 | 1 次 |
| 是否需要 level 标记 | 需要 | 不需要 |
| 增加维度 | 修改 SQL 和合并逻辑 | 匹配器自动适配 |
| 去重依据 | 外部 level | 精确值数量 |
| 最终结果 | 一致 | 一致 |

> ⚠️ 全量方案适合菜单配置这种规模可控的数据。如果配置量非常大，需要结合缓存、索引或数据库侧过滤，不能无上限全表加载。

## 🔥 面试要点

**Q1：为什么不用逐级 Fallback？**

> **面试话术**：*"逐级查询会产生多次 SQL 和多个菜单池，合并时需要额外 level 标记去重，增加维度还要修改查询次数和合并逻辑。全量匹配一次查询拿到候选集，逐条通配匹配，最后按 node_id 保留精确值最多的记录，逻辑更集中。"*

**Q2：如何保证同一 node_id 的精确版本优先？**

> **面试话术**：*"比较 country、entity、channel、branch 四个维度里有多少个是具体值而不是通配符。精确值越多代表约束越具体，同一 node_id 只保留精确值数量最多的一条。"*

## 🔄 知识闭环

```java
请求四维参数
  → 全量读取配置
  → 逐条 wildcardMatch
  → 保留匹配记录
  → 按 node_id 精确优先去重
  → 交给权限过滤
  → 组树返回
```
