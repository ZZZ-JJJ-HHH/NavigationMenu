## 📌 一句话核心

> <span style="color:red">**从平铺记录（每条只知自己 parentId）到嵌套树（JSON children），单趟 idMap 法 O(n) 最优选。**</span>

---

## 🎯 背景与问题

### 这个问题在哪些场景出现

| 场景 | 平铺结构特征 | 需要输出的结构 |
|------|------------|---------------|
| 导航菜单 | menu_config 表，每条有 parent_id | 嵌套 JSON：{nodeId, children:[...]} |
| 组织架构 | department 表，parent_id 指向上级部门 | 树形组织图 |
| 评论回复 | comment 表，reply_to_id | 嵌套回复列表 |
| 地区选择器 | region 表，parent_id | 省 -> 市 -> 区三级联动 |

### 没有好方案时的痛点

| 痛点 | 具体表现 |
|------|---------|
| 递归栈溢出 | 用递归法，树一深（几十层）就栈爆了 |
| 性能差 | O(n^2) 方案里的 findMenuId 反查，每次遍历全量数据 |
| 逻辑绕 | 两趟 childrenMap 法的反查 nodeId -> id 逻辑，写出来自己都懵 |

## 💡 核心目的

**给一份平铺数据，高效地组装成嵌套树。设计目标：**

1. **时间复杂度 O(n)**：遍历一次搞定
2. **不依赖递归**：无栈深度限制
3. **代码清晰**：逻辑读一眼能懂，别玩花活

### 约定：根节点的 parentId

不同系统对"根节点"的标记不一样：有的用 null，有的用 0，有的用 -1。**本项目数据库用 0**，代码里同时兼容 null 和 0。

## ⚙️ 原理与机制

### 示例数据（三种方案都用同一份）

```text
id | nodeId   | nodeName   | parentId | sortOrder
---|----------|------------|----------|-----------
 1 | home     | 首页        | 0        | 1
 2 | account  | 我的账户    | 0        | 2
 3 | transfer | 转账汇款    | 0        | 3
 4 | inner    | 行内转账    | 3        | 1
 5 | cross    | 跨行转账    | 3        | 2
 6 | digital  | 数字人民币  | 2        | 1
```

**目标输出**：
```json
[
  { "nodeId": "home", "nodeName": "首页" },
  {
    "nodeId": "account",
    "nodeName": "我的账户",
    "children": [{ "nodeId": "digital", "nodeName": "数字人民币" }]
  },
  {
    "nodeId": "transfer",
    "nodeName": "转账汇款",
    "children": [
      { "nodeId": "inner", "nodeName": "行内转账" },
      { "nodeId": "cross", "nodeName": "跨行转账" }
    ]
  }
]
```

### 方案一：两趟 childrenMap 法

**核心思路**：第一趟按 parentId 分组建索引表（父id -> 孩子列表），第二趟遍历每个节点，用 findMenuId 反查它自己的 id 在不在索引表里，在就把孩子挂上去。

```java
public List<MenuNodeVO> build(List<MenuConfig> menus) {
    // 1. 排序
    List<MenuConfig> sorted = menus.stream()
            .sorted(Comparator.comparingInt(m -> m.getSortOrder() != null ? m.getSortOrder() : 0))
            .toList();

    // 2. 第一趟：建索引表
    Map<Long, List<MenuNodeVO>> childrenMap = new LinkedHashMap<>();
    for (MenuConfig menu : sorted) {
        Long parentKey = (menu.getParentId() == null || menu.getParentId() == 0L)
            ? 0L : menu.getParentId();
        childrenMap.computeIfAbsent(parentKey, k -> new ArrayList<>())
                   .add(convert(menu));
    }

    // 3. 第二趟：逐个挂孩子（findMenuId 是 O(n) 反查！）
    for (Map.Entry<Long, List<MenuNodeVO>> entry : childrenMap.entrySet()) {
        for (MenuNodeVO child : entry.getValue()) {
            Long childId = findMenuId(sorted, child.getNodeId());
            if (childId != null && childrenMap.containsKey(childId)) {
                child.setChildren(childrenMap.get(childId));
            }
        }
    }
    return childrenMap.getOrDefault(0L, new ArrayList<>());
}
```

**执行过程**：
```text
2. 第一趟后（扁平索引）：
  key=0L -> [首页, 我的账户, 转账汇款]
  key=2L -> [数字人民币]
  key=3L -> [行内转账, 跨行转账]

3. 第二趟：
  我的账户 -> findMenuId("account")=2 -> childrenMap.containsKey(2L)? 有！-> setChildren([数字人民币])
  转账汇款 -> findMenuId("transfer")=3 -> childrenMap.containsKey(3L)? 有！-> setChildren([行内转账,跨行转账])
```

| 优点 | 缺点 |
|------|------|
| 不依赖递归 | 两趟循环 |
| 中间状态可观察 | findMenuId 是 O(n) 反查 -> 整体 O(n^2) |
|  | 反查逻辑绕，写起来费劲 |

### 方案二：单趟 idMap 法（推荐 ✅）

**核心思路**：先建 id -> VO 的直接索引（一次转换），然后单趟遍历每个节点：**没爹 -> 加根列表；有爹 -> 从 idMap O(1) 找到爹，挂上去**。

```java
public List<MenuNodeVO> build(List<MenuConfig> menus) {
    // 1. 排序
    List<MenuConfig> sorted = menus.stream()
            .sorted(Comparator.comparingInt(m -> m.getSortOrder() != null ? m.getSortOrder() : 0))
            .toList();

    // 2. 建 id -> VO 直接索引（一次转换）
    Map<Long, MenuNodeVO> idMap = new LinkedHashMap<>();
    for (MenuConfig menu : sorted) {
        idMap.put(menu.getId(), convert(menu));
    }

    // 3. 单趟：找爹挂上去
    List<MenuNodeVO> roots = new ArrayList<>();
    for (MenuConfig menu : sorted) {
        MenuNodeVO node = idMap.get(menu.getId());
        Long parentId = menu.getParentId();

        if (parentId == null || parentId == 0L) {
            roots.add(node);                          // 没爹 -> 根节点
        } else {
            MenuNodeVO parent = idMap.get(parentId);  // O(1) 找爹
            if (parent != null) {
                if (parent.getChildren() == null) {
                    parent.setChildren(new ArrayList<>());
                }
                parent.getChildren().add(node);      // 挂上去
            }
        }
    }
    return roots;
}
```

**执行过程**：
```text
2. idMap：{1->首页, 2->我的账户, 3->转账汇款, 4->行内转账, 5->跨行转账, 6->数字人民币}

3. 单趟遍历（"找爹挂上去"）：
  menu{id:1, parentId:0}   -> 没爹 -> roots.add(首页)
  menu{id:2, parentId:0}   -> 没爹 -> roots.add(我的账户)
  menu{id:3, parentId:0}   -> 没爹 -> roots.add(转账汇款)
  menu{id:4, parentId:3}   -> idMap.get(3)=转账汇款 -> 转账汇款.children.add(行内转账)
  menu{id:5, parentId:3}   -> idMap.get(3)=转账汇款 -> 转账汇款.children.add(跨行转账)
  menu{id:6, parentId:2}   -> idMap.get(2)=我的账户 -> 我的账户.children.add(数字人民币)
```

结束，roots 就是完整嵌套树。

| 优点 | 缺点 |
|------|------|
| **单趟，O(n)** | 无明显缺点 |
| 不需要反查，主键直接定位 |  |
| "找爹挂上去"逻辑超级直观 |  |
| 代码量最少 |  |

### 方案三：递归法

**核心思路**：从根开始递归，给一个父 id，返回它下面的完整子树。

```java
public List<MenuNodeVO> build(List<MenuConfig> menus) {
    // 1. 排序（同上）
    // 2. 按 parentId 分组（和方案一第一趟相同）
    Map<Long, List<MenuConfig>> childrenMap = new LinkedHashMap<>();
    for (MenuConfig menu : menus) {
        Long parentKey = (menu.getParentId() == null || menu.getParentId() == 0L)
            ? 0L : menu.getParentId();
        childrenMap.computeIfAbsent(parentKey, k -> new ArrayList<>()).add(menu);
    }
    // 3. 从根开始递归
    return buildTree(childrenMap, 0L);
}

// 递归：给一个父 id，返回完整子树
private List<MenuNodeVO> buildTree(Map<Long, List<MenuConfig>> childrenMap, Long parentId) {
    List<MenuConfig> kids = childrenMap.get(parentId);
    if (kids == null) return Collections.emptyList();

    List<MenuNodeVO> result = new ArrayList<>();
    for (MenuConfig kid : kids) {
        MenuNodeVO vo = convert(kid);
        vo.setChildren(buildTree(childrenMap, kid.getId()));  // 递归！
        result.add(vo);
    }
    return result;
}
```

**执行过程**：
```text
buildTree(childrenMap, 0L)
  -> kids = [首页, 我的账户, 转账汇款]

  首页: buildTree(childrenMap, 1L) -> kids = null -> return []
  我的账户: buildTree(childrenMap, 2L)
    -> kids = [数字人民币]
    数字人民币: buildTree(childrenMap, 6L) -> kids = null -> return []
    -> 我的账户.children = [数字人民币]
  转账汇款: buildTree(childrenMap, 3L)
    -> kids = [行内转账, 跨行转账] -> 递归每个 -> children = [行内转账,跨行转账]

最终 return [首页, 我的账户{children:[数字人民币]}, 转账汇款{children:[行内转账,跨行转账]}]
```

| 优点 | 缺点 |
|------|------|
| 代码最简洁优雅 | Java 默认栈深度有限（菜单一般 3-4 层，远不会触发） |
| 天然适配任意深度 | 递归对新手不友好，容易栈溢出 |

## 📊 应用与对比

### 三种方案横向对比

| 维度 | 方案一：两趟 childrenMap | 方案二：单趟 idMap ✅ | 方案三：递归 |
|------|------------------------|----------------------|-------------|
| **遍历趟数** | 2 趟 | **1 趟** | 1 趟（递归调用） |
| **时间复杂度** | O(n^2) <- findMenuId | **O(n)** | O(n) |
| **代码量** | 多 | **少** | 最少 |
| **理解难度** | 中（反查逻辑绕） | **低（找爹挂上去很直观）** | 中（递归需要点感觉） |
| **栈深度限制** | 无 | **无** | Java 默认约 10000（菜单远不够） |
| **适合场景** | 需要打印中间状态调试 | **通用场景，首选** | 树层级很深且天然递归思维 |

### 本项目的选择

**选了方案二（单趟 idMap）**，原因：
- 时间复杂度 **O(n)**，比方案一的 O(n^2) 好
- **代码量最少**，"找爹挂上去"逻辑一眼能懂
- 不依赖递归，**无栈深度顾虑**
- 用数据库主键直接定位，**不需要反查 nodeId -> id**

### 踩坑记录：根节点 parentId 的判定

> **问题**：直接抄方案二代码，把 parentId == null 当成根节点，结果返回空树。
>
> **根因**：数据库里 parent_id 存的是 **0**，不是 null。
>
> **日志证据**：
> ```
> menu[id=1] parentId=0, parent found=false
> menu[id=2] parentId=0, parent found=false
> ...所有根节点都没进根分支！
> tree built, roots=0
> ```
>
> **修复**：根节点判定必须同时兼容 null 和 0（以及可能的 -1）：
> ```java
> if (parentId == null || parentId == 0L) {
>     roots.add(node);
> }
> ```
>
> **教训**：写代码之前先看一眼数据库里的实际数据，**别脑补约定**！

## 🔥 面试要点

### 高频问题 + 标准答案

**Q: 你那个树构建用的什么算法？时间复杂度多少？**
> "用的**单趟 idMap 法**，时间复杂度 **O(n)**。核心思路是先建 id -> VO 的直接索引表，然后单趟遍历每个节点：没爹加根列表，有爹从 idMap 里 O(1) 找到爹挂上去。比递归法少了递归开销，比两趟 childrenMap 法少了 O(n^2) 的反查。"

**Q: 为什么不用递归？递归写起来更短啊？**
> "递归确实写起来最简洁，但有两个问题。第一，栈深度限制——虽然菜单一般 3-4 层远不会爆，但组织架构可能几十层。第二，团队维护性——很多同学对递归不敏感，单趟 idMap 法的'找爹挂上去'逻辑更直观，一眼能懂。性能上两者都是 O(n)，但单趟法没有递归调用开销。"

**Q: idMap 法的代码贴一下？**
> （直接贴方案二的代码，重点讲 parentId == null \|\| parentId == 0L 的兼容处理）

**Q: 你踩过什么坑？**
> "根节点判定的坑。一开始想当然认为数据库里 parent_id 存的是 null，结果实际是 0。代码里只写了 parentId == null，所有根节点都没进根分支，返回了空树。**教训是写代码之前先看实际数据，别脑补约定**。"

## 🔄 知识闭环

### 树构建在项目链路中的位置

```text
整体请求链路：

前端请求
  |
  v
Service.buildMenuTree()
  |
  +---> Redis CacheService.get()    <- 11-业务架构-Redis缓存
  |         |    (命中直接返回，不往下走)
  |         |
  |    未命中 v
  |
  +---> HandlerChain.proceed()      <- 10-业务架构-责任链模式
           |
           +-- LegacyCheckHandler  @Order(1)   查旧系统
           +-- LoadMenuHandler     @Order(2)   拉菜单（DB）
           +-- FallbackMatchHandler @Order(3)  四维匹配
           +-- PermissionFilterHandler @Order(4) 权限过滤
           |
           +-- TreeBuildHandler    @Order(5)   <- 就是本篇讲的：
                                                  单趟 idMap 法组树 ✅
```

### 三者闭环关系

| 专题 | 在链路中的位置 | 解决什么 | 算法/模式 |
|------|--------------|---------|---------|
| **10-责任链模式** | Service 层内部 | 解耦 5 步硬编码流水线 | Handler + @Order + Context |
| **11-Redis缓存** | Service 层前置 | 95%+ 请求直接拦截 | Cache-Aside + 两级 key |
| **13-树构建方案（本篇）** | TreeBuildHandler 内部 | O(n) 把平铺数据组树 | 单趟 idMap 法 |

**三者共同提升了核心链路**：Redis 先挡掉大部分请求 -> 挡不住的走可插拔的责任链 -> 链里最耗时的组树用最优算法。最终效果：**单请求从 300ms+ -> 命中 < 1ms / miss ~10ms。**
