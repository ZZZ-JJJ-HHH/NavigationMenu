## 🎯 背景与问题

### 原来的代码长什么样（硬编码 5 步流水线）

重构前的 MenuServiceImpl（伪代码还原）：

`java
public MenuTreeVO buildMenuTree(MenuQueryDTO dto) {
    // Step 1: Legacy 分流
    BranchConfig branch = branchConfigMapper.selectOne(...);
    if (branch != null && branch.getUseLegacyMenu() == 1) {
        return new MenuTreeVO(Collections.emptyList(), null);  // 提前返回
    }

    // Step 2: 加载菜单
    List<MenuConfig> allMenus = menuConfigMapper.selectList(...);

    // Step 3: Fallback 匹配
    List<MenuConfig> matched = fallbackService.match(allMenus, ...);

    // Step 4: 权限过滤
    Set<String> userPerms = mockUserPermissions(dto.getUserId());
    List<MenuConfig> filtered = permissionFilter.filter(matched, userPerms);

    // Step 5: 组树
    List<MenuNodeVO> tree = treeBuilder.build(filtered);
    return new MenuTreeVO(tree, null);
}
`

### 这段代码有什么问题

| # | 问题 | 具体表现 |
|---|------|---------|
| 1 | **单方法臃肿** | 80+ 行，5 个 Step 注释才能勉强区分 |
| 2 | **步骤写死** | 想调整顺序、想插入新步骤（比如限流），都要改这个方法 |
| 3 | **变量传递混乱** | allMenus -> matched -> filtered，链式依赖，中间改了变量名后面全报错 |
| 4 | **无法独立测试** | 想单独测 Legacy 分流，必须 mock 所有依赖 |
| 5 | **无日志可见链路** | 出问题不知道卡在哪一步，只能打断点 |

### 核心痛点

> **"这个方法知道太多、做了太多、改起来太痛。"**

---

## 💡 核心目的

**把 5 步硬编码流水线改造成可插拔的 Handler 链。设计目标：**

1. **解耦**：每个步骤只关心自己的输入输出，不知道其他步骤的存在
2. **开闭原则**：加新步骤只需要**新建一个 Handler 类**，零修改老代码
3. **可观测**：Chain 自动打 chain step: XxxHandler 日志（DEBUG 级），把闸门打开就能看见执行顺序

## ⚙️ 原理与机制

### 四个核心组件

| 组件 | 职责 | 类比 |
|------|------|------|
| **Handler 接口** | 定义统一的 handle(MenuContext context) 方法 | 分拣员"工种"的招聘要求 |
| **Concrete Handler** | 实现具体业务逻辑 | 张三查 Legacy、李四拉菜单、王五匹配 |
| **Chain** | 持有所有 Handler，按 @Order 排序执行，检测终止信号 | 传送带的调度系统 |
| **Context** | 贯穿整条链的数据公文包 | 包裹 / 病历本 |

### 链路流程

1. **Service 层**（现在只剩 45 行）：缓存 miss 时创建 MenuContext，调用 handlerChain.proceed(context)
2. **MenuHandlerChain**：遍历所有 Handler，按 @Order 排序后依次调用
3. **每个 Handler**：
   - 从 Context 读前一步的输出
   - 执行自己的业务逻辑
   - 往 Context 写自己的输出
   - 如果设置了 context.result（非 null），Chain 检测到后**终止整条链**
4. **Chain 终止后**：Service 从 context.result 拿最终结果，回写缓存

### 核心代码逐个看

#### Handler 接口（3 行）

`java
// service/chain/MenuHandler.java
public interface MenuHandler {
    void handle(MenuContext context);
}
`

**为什么不需要 chain 参数**？因为我们的 Chain 自己遍历推进，Handler 只需要关心处理 context。经典责任链才需要 chain 参数（Handler 自己调 chain.proceed()），但我们选了 Chain 管推进的模式。

#### Context（数据公文包）

`java
// service/chain/MenuContext.java
@Data
public class MenuContext {
    private MenuQueryDTO query;       // 入参
    private List<MenuConfig> allMenus; // Step 2 写
    private List<MenuConfig> matched;  // Step 3 写
    private Set<String> userPerms;     // Step 4 读
    private List<MenuConfig> filtered; // Step 4 写
    private List<MenuNodeVO> tree;     // Step 5 写
    private MenuTreeVO result;         // Step 5 写 -> 链终止信号
}
`

**关键约定**：谁设置了 esult，Chain 就停。这是终止链的**唯一方式**。

#### Chain（调度中心）

`java
// service/chain/MenuHandlerChain.java
@Component
@Slf4j
public class MenuHandlerChain {

    private final List<MenuHandler> sortedHandlers;

    // Spring 自动注入所有 MenuHandler 实现类
    // 构造时按 @Order 注解排序
    public MenuHandlerChain(List<MenuHandler> handlers) {
        this.sortedHandlers = handlers.stream()
                .sorted(Comparator.comparingInt(h -> {
                    Order order = h.getClass().getAnnotation(Order.class);
                    return order != null ? order.value() : Integer.MAX_VALUE;
                }))
                .toList();
    }

    public void proceed(MenuContext context) {
        for (MenuHandler handler : sortedHandlers) {
            log.debug("chain step: {}", handler.getClass().getSimpleName());
            handler.handle(context);
            if (context.getResult() != null) {
                log.info("chain terminated at {}", handler.getClass().getSimpleName());
                return;
            }
        }
    }
}
`

**两个关键设计**：
1. **自动排序**：Spring 把所有 @Component 的 Handler 注入进来，读 @Order 注解排序。忘了加 @Order -> 排到最后。
2. **自动终止检测**：每个 Handler 执行完，Chain 检查 context.result。有结果就 return，没结果继续。

#### 5 个 Handler（每个只做一件事）

**LegacyCheckHandler（@Order(1)）**：
`java
@Component
@Order(1)
@RequiredArgsConstructor
@Slf4j
public class LegacyCheckHandler implements MenuHandler {

    private final BranchConfigMapper branchConfigMapper;

    @Override
    public void handle(MenuContext context) {
        BranchConfig branch = branchConfigMapper.selectOne(...);
        if (branch != null && branch.getUseLegacyMenu() == 1) {
            context.setResult(new MenuTreeVO(Collections.emptyList(), null));  // 链终止！
            return;
        }
        // 不是 legacy -> 什么都不做，Chain 自动继续下一个
    }
}
`

**LoadMenuHandler（@Order(2)）**：
`java
@Component
@Order(2)
@RequiredArgsConstructor
@Slf4j
public class LoadMenuHandler implements MenuHandler {

    private final MenuConfigMapper menuConfigMapper;

    @Override
    public void handle(MenuContext context) {
        List<MenuConfig> allMenus = menuConfigMapper.selectList(...);
        context.setAllMenus(allMenus);  // 写入 context，给后面 Handler 用
    }
}
`

**FallbackMatchHandler（@Order(3)）**：
`java
@Component
@Order(3)
@RequiredArgsConstructor
@Slf4j
public class FallbackMatchHandler implements MenuHandler {

    private final MenuFallbackService fallbackService;

    @Override
    public void handle(MenuContext context) {
        var matched = fallbackService.match(
            context.getAllMenus(),  // 读 Step 2 的输出
            context.getQuery().getCountryCode(),
            // ...
        );
        context.setMatched(matched);
    }
}
`

**PermissionFilterHandler（@Order(4)）** 和 **TreeBuildHandler（@Order(5)）** 同理——各自只做一件事，从 context 读前一步输出，写自己的输出。

#### 现在的 MenuServiceImpl（45 行）

`java
@Service
@RequiredArgsConstructor
@Slf4j
public class MenuServiceImpl implements MenuService {

    private final MenuTreeCacheService cacheService;
    private final MenuHandlerChain handlerChain;

    @Override
    public MenuTreeVO buildMenuTree(MenuQueryDTO dto) {
        log.info("buildMenuTree start, query: {}", dto);

        // 1. 先查缓存
        MenuTreeVO cached = cacheService.get(dto.getBranchCode(), dto.getUserId());
        if (cached != null) return cached;

        // 2. 缓存 miss -> 走责任链
        MenuContext context = new MenuContext();
        context.setQuery(dto);
        handlerChain.proceed(context);

        // 3. Chain 走完，拿结果 + 回写缓存
        MenuTreeVO result = context.getResult();
        if (result == null) {
            throw new IllegalStateException("menu handler chain produced no result");
        }
        cacheService.put(dto.getBranchCode(), dto.getUserId(), result);
        return result;
    }
}
`

**Service 层现在只做两件事**：缓存编排 + Chain 调用。业务逻辑全在 Handler 里。

## 📊 应用与对比

### 改动成本对比

**场景**：新增一步"限流检查"——每秒超过 100 请求直接返回空树。

| 做法 | 改多少代码 | 改多少老代码 |
|------|-----------|-------------|
| 硬编码 | 在 Service 方法里加 8 行 | **1 个方法**（80 行 -> 88 行，改老代码有风险） |
| 责任链 | **新建 1 个类**（RateLimitHandler，25 行） | **0 行**老代码 |

### 问题解决清单

| 原来的问题 | 责任链怎么解决 |
|-----------|--------------|
| 单方法 80+ 行 | 每个 Handler 类 25 行以内 |
| 步骤写死 | @Order 注解声明顺序，改顺序只改注解值 |
| 变量传递混乱 | MenuContext 统一承载，字段名一目了然 |
| 无法独立测试 | 每个 Handler 是独立 Spring Bean，可以单独 mock、单独测 |
| 链路不透明 | Chain 自动打 chain step: XxxHandler（DEBUG 级），把闸门打开顺序一眼看见 |

### 两种 Chain 实现的对比

| 维度 | 经典责任链（Handler 调 chain.proceed） | 我们的实现（Chain 自己遍历） |
|------|---------------------------------------|--------------------------|
| **推进方式** | Handler 手动调 chain.proceed() | Chain 在 proceed() 里自己遍历 |
| **终止方式** | Handler 不调 proceed 就终止 | Handler 设 context.result != null 就终止 |
| **Handler 要不要 chain 参数** | 必须要 | 完全不需要 |
| **Handler 依赖** | 同时知道 Context 和 Chain | 只知道 Context，更解耦 |
| **可读性** | Handler 里混着业务逻辑和推进逻辑 | Handler 只写业务，Chain 只管编排 |

### 和其他设计模式对比

| 模式 | 本质差异 | 适用场景 |
|------|---------|---------|
| **责任链（我们）** | 业务步骤的**可插拔编排** | >= 4 步的复杂流水线 |
| **AOP** | 横切关注点（日志、事务）**织入**方法 | 统一处理某类关注点 |
| **模板方法** | 继承，子类实现抽象方法 | 固定骨架，可替换某些步骤 |
| **策略模式** | 多个算法**切换**一个 | 根据条件选一个算法 |
| **简单硬编码** | 直接按顺序写 | <= 3 步的简单流程 |

### 代价分析

| 代价 | 说明 | 我们项目里要不要紧 |
|------|------|------------------|
| **类数量增加** | 1 个方法 -> 5 个 Handler + Chain + Context + 接口 = 8 个类 | 不要紧。职责清晰比类数量重要 |
| **调试链路变长** | 出问题要顺着 Chain 看哪个 Handler 搞坏了 | 不要紧。把闸门开到 DEBUG，chain step 日志帮你定位 |
| **Spring Bean 装配** | 每个 Handler 都是 @Component | 不要紧。5 个类启动零影响 |
| **过度设计风险** | 业务只有 2 步，拆成 2 个 Handler 反而啰嗦 | 不要紧。我们正好 5 步，值得拆 |

## 🔥 面试要点

### 高频问题 + 标准答案

**Q: 你的责任链怎么实现的？**
> "我定义了 MenuHandler 接口（3 行，就一个 handle(MenuContext context) 方法）、MenuHandlerChain 链本体、MenuContext 贯穿整条链的公文包，加 5 个 Handler 实现类。Spring 自动注入所有 Handler，Chain 构造时按 @Order 注解排序执行。每个 Handler 只做一件事——查 Legacy、拉菜单、Fallback 匹配、权限过滤、组树。某个 Handler 设置 context.result 就终止链。Service 层现在只剩缓存检查 + Chain 调用 + 缓存回写 45 行。"

**Q: Chain 怎么知道 Handler 的顺序？**
> "Spring 自动注入所有 MenuHandler 实现类到 List<MenuHandler>，Chain 构造时读每个类的 @Order 注解排序。忘了加 @Order 会排到 Integer.MAX_VALUE（最后）——启动就能发现遗漏。"

**Q: 怎么终止链？**
> "Handler 往 MenuContext.result 里塞一个非 null 对象，Chain 在每次 handle() 后检查 result 是否为 null，不为 null 就 return。LegacyCheckHandler 就是这么干的——这个分行走旧系统，直接设置空树结果，后面 4 个 Handler 都不跑了。"

**Q: Handler 里为什么没有 chain 参数？经典责任链不是要调 chain.proceed() 吗？**
> "好问题！经典责任链确实是 Handler 自己调 chain.proceed() 推进，但我们选了 Chain 自己遍历推进的模式。Chain 在 proceed() 里 for 循环调 handler.handle(context)，然后检查 result。Handler 只需要关心处理 context，**不需要也不应该知道 Chain 的存在**——依赖方向更清晰。5 个 Handler 全 import 了 chain 但没一个真调，说明参数多余，果断删掉。"

**Q: 加个新步骤要改多少代码？**
> "**0 行老代码，新建 1 个类**。比如加限流检查：@Component @Order(3) public class RateLimitHandler implements MenuHandler { public void handle(MenuContext ctx) { ... } }，老代码一个字不动，Spring 自动扫描、Chain 自动排序、自动执行。这就是开闭原则。"

**Q: 和 AOP 有什么区别？**
> "AOP 是**横切关注点**（日志、事务、权限校验），织入点是方法。责任链是**业务步骤的编排**，每个步骤有明确的输入输出。AOP 是'在原方法前后插东西'，责任链是'把原方法拆成多段编排'。两者解决的是完全不同的问题。"

**Q: 为什么不用模板方法？**
> "模板方法是**继承**，子类继承父类、实现抽象方法。但 Java 单继承，而且 5 个 Handler 之间没有继承关系。责任链是**组合**——Spring 注入所有 Handler，Chain 统一编排——更灵活，更符合组合优于继承的原则。"

`

## 🔄 知识闭环

### 责任链在整体链路中的位置

1. 前端请求到达 Controller
2. Controller 校验参数后调用 Service.buildMenuTree()
3. Service 先查 **Redis 缓存**（见 11-技术专题）
   - 命中：直接返回，链路结束
   - 未命中：往下走
4. Service 创建 MenuContext，调用 **HandlerChain.proceed()**（就是本篇讲的）
   - Chain 按 @Order 依次执行 5 个 Handler
   - LegacyCheckHandler @Order(1) 查旧系统（DB）
   - LoadMenuHandler @Order(2) 拉菜单（DB）
   - FallbackMatchHandler @Order(3) 四维匹配
   - PermissionFilterHandler @Order(4) 权限过滤
   - TreeBuildHandler @Order(5) O(n) 组树（见 13-技术专题）
   - 任何 Handler 设置了 context.result，Chain 立即终止
5. Chain 走完，Service 从 context.result 拿菜单树
6. **Redis 回写缓存**（11-技术专题）
7. 返回

### 三个技术专题的闭环关系

| 专题 | 在链路中的位置 | 解决什么 | 模式/算法 |
|------|--------------|---------|---------|
| **10-责任链模式（本篇）** | Service 层内部 | 解耦 5 步硬编码流水线 | Handler + @Order + Context |
| 11-Redis缓存 | Service 层前置 | 95%+ 请求直接拦截 | Cache-Aside + 两级 key |
| 13-树构建方案 | TreeBuildHandler 内部 | O(n) 把平铺数据组树 | 单趟 idMap 法 |

**三者形成层层递进的优化链**：Redis 先挡掉大部分请求 -> 挡不住的走可插拔的责任链 -> 链里最后一步用最优树算法。最终效果：**单请求从 300ms+（2 次 DB + 完整链）-> 命中 < 1ms / miss ~10ms。**
