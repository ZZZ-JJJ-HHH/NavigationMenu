## 📌 一句话核心

> <span style="color:red">**日志 API 和日志实现是两层，绑定在运行时自动完成；但第三方库不一定守这套分层 —— 动日志配置之前，先确认"哪些日志受你管辖"。**</span>

---

## 🎯 背景与问题

### 两个真实困惑

写日志的人几乎都会撞上这两件事：

| 困惑 | 表面现象 | 真实原因 |
|:---|:---|:---|
| "pom 里没写 logback，它从哪来的？" | 加个 `@Slf4j` 就能用，配置里却找不到 logback 依赖 | Maven 传递依赖，starter 把整套日志实现带了进来 |
| "我明明配了级别，为什么这条日志不受影响？" | 级别改了，某类日志照打不误 | 它根本没走 SLF4J，不在 logback 的管辖范围内 |

这两个问题看着无关，其实是同一件事的两面：**你的日志到底经过哪几层、受谁管**。

> ⚠️ **管辖之外，配置皆无效。** 这是本篇要说清的唯一一件事。日志级别、格式、输出路径、采集规则 —— 全都作用在"受管辖"的日志上；不受管辖的那些，你写什么配置它都不理你。

---

## 💡 核心目的

读完能回答三个问题：

1. **日志从哪来**：classpath 里的日志实现是谁带进来的？
2. **谁在管事**：`log.info()` 是怎么变成文件里那行的？
3. **哪些我管不到**：还有没有日志绕过了这套体系？

前两个问题决定你能不能读懂构建产物，第三个问题决定你的日志配置**是不是真的生效**。

## ⚙️ 原理与机制

### 门面与实现：日志是分层的

```java
┌──────────────┐        ┌──────────────┐        ┌──────────────┐
│  log.info()  │───────▶│    SLF4J     │───────▶│   logback    │───▶ 文件 / stdout
│  业务代码    │        │   门面       │        │   实现       │
└──────────────┘        └──────────────┘        └──────────────┘
   只认接口                 不输出日志              真正干活
```

| 层 | 代表 | 干什么 | 不干什么 |
|:---|:---|:---|:---|
| 门面（API） | SLF4J | 定义 `Logger` 接口：`log.info(...)` | 自己不输出任何日志 |
| 实现（后端） | logback、log4j2 | 判级别、格式化、写文件、做轮转 | 不定义业务代码要用的那套接口 |
| 桥接（适配器） | `log4j-slf4j2-impl`、`jul-to-slf4j` | 把别的日志框架接到 SLF4J 上 | 不是必需品，只在混用多套框架时才要 |

> 🔑 **门面的价值是解耦**：业务代码只认 `org.slf4j.Logger` 这一个接口，将来把 logback 换成 log4j2，业务代码一行都不用改。logback 和 SLF4J 是同一个作者写的，属于原生实现，所以本项目一个适配器都不需要。

### logback 是从哪来的

先把"依赖"和"配置"分开，这是两件事：

| | 由什么决定 | 在哪看 |
|:---|:---|:---|
| **依赖**：logback 的 jar 在不在 classpath | Maven 传递依赖 | `mvn dependency:tree`、打包后的 `BOOT-INF/lib/` |
| **配置**：日志怎么输出、输出到哪 | `logback-spring.xml` | 项目 resources 目录 |

`logback-spring.xml` 只解决第二行。第一行在你写下第一行 `@Slf4j` 之前就已经就位了。

logback 是 `spring-boot-starter-web` 顺带带进来的。本项目实测的依赖树：

```
+- org.springframework.boot:spring-boot-starter-web:jar:3.4.4:compile
|  \- org.springframework.boot:spring-boot-starter:jar:3.4.4:compile
|     \- org.springframework.boot:spring-boot-starter-logging:jar:3.4.4:compile
|        +- ch.qos.logback:logback-classic:jar:1.5.18:compile
|        |  \- ch.qos.logback:logback-core:jar:1.5.18:compile
|        \- org.slf4j:jul-to-slf4j:jar:2.0.17:compile
```

链路是 `spring-boot-starter-web` → `spring-boot-starter` → **`spring-boot-starter-logging`** → `logback-classic` + `logback-core`。所以 pom 里搜 `logback`，只会搜到你自己加的那个 `logstash-logback-encoder`，搜不到 logback 本身。这就是 Maven 的传递依赖：**starter 负责把一整套常用依赖打包带进来，你只需要声明 starter。**

打包之后，实物长这样（`target/*.jar` 里的 `BOOT-INF/lib/`）：

```
BOOT-INF/lib/slf4j-api-2.0.17.jar          ← 门面，代码里 import 的就是它
BOOT-INF/lib/logback-classic-1.5.18.jar    ← 实现，真正干活的
BOOT-INF/lib/logback-core-1.5.18.jar
BOOT-INF/lib/jul-to-slf4j-2.0.17.jar       ← 把 java.util.logging 桥接到 SLF4J
BOOT-INF/lib/log4j-to-slf4j-2.24.3.jar     ← 把 log4j2 的 API 桥接到 SLF4J
BOOT-INF/lib/log4j-api-2.24.3.jar
```

后两个桥接包是给第三方库准备的：某些库内部用的是 JUL 或 log4j2 的 API，Spring Boot 把它们统一路由到 SLF4J，这样全项目的日志都走同一条出口。

### 绑定是怎么发生的

绑定关系**不在你的代码里**，而是运行时在 classpath 里自动发现的，机制是 Java 的 ServiceLoader。打开 `logback-classic` 的 jar，里面有这个文件：

```
META-INF/services/org.slf4j.spi.SLF4JServiceProvider
```

内容只有一行：

```
ch.qos.logback.classic.spi.LogbackServiceProvider
```

SLF4J 初始化时扫描 classpath，读到这个文件，就实例化里面写的那个类，从此所有 `log.info()` 都转发给它。

> 🔑 **门面与实现的解耦，落地方式就是这个**：业务代码只 import SLF4J，绑定是运行时自动完成的，所以换实现不用改业务代码。

> 📌 一个历史细节：SLF4J 1.x 用的是 `org.slf4j.impl.StaticLoggerBinder` 这个静态绑定类，2.0 才改成 ServiceLoader。本项目是 SLF4J 2.0.17，走的是后者。

### logback-spring.xml 是覆盖，不是启用

一个容易被误解的点：**这份文件是"覆盖默认配置"，不是"启用 logback"**。Spring Boot 启动时，`LogbackLoggingSystem` 按固定顺序在 classpath 里找配置文件：

```
logback-spring.xml → logback-spring.groovy → logback.xml → logback.groovy
```

找到 `logback-spring.xml` 就用它；找不到，Spring Boot 还有自己的一套默认配置（控制台彩色输出，格式里带进程 PID）。

> ⚠️ **所以准确的因果是**：logback 本来就在工作，这份文件只是把它默认的输出方式换成了你要的样子。不加它，日志照样打，只是格式不是你想要的。

一个反证：如果哪天要把实现换成 log4j2，第一步是在 `spring-boot-starter-web` 里**排除 `spring-boot-starter-logging`**，再加 `spring-boot-starter-log4j2`。需要"排除"，恰恰说明 logback 是被 starter 自动带进来的。

自己怎么复现：

```powershell
mvn dependency:tree -Dincludes="ch.qos.logback:*,org.slf4j:*"

Add-Type -AssemblyName System.IO.Compression.FileSystem
$z = [System.IO.Compression.ZipFile]::OpenRead("target/NavigationMenu-0.0.1-SNAPSHOT.jar")
$z.Entries | Where-Object { $_.FullName -match 'BOOT-INF/lib/.*(logback|slf4j)' } | ForEach-Object { $_.FullName }
$z.Dispose()
```

### 有些日志不走 SLF4J

上面那条链路成立，靠的是一个前提：**打日志的人老老实实用了 SLF4J**。第三方库不一定这么干。

MyBatis 就属于"不老实"的那一类。**它不直接用 SLF4J**，而是自己定义了一套日志抽象，目的就是能兼容"用户环境里碰巧装了哪套日志框架"：

| MyBatis 的 `Log` 实现 | 转交给谁 | 受 logback 管辖吗 |
|:---|:---|:---|
| `StdOutImpl` | 直接 `System.out` | **不受** |
| `Slf4jImpl` | SLF4J → logback | 受 |
| `Log4j2Impl` / `Log4jImpl` | log4j2 / log4j | 受（前提是你用 log4j2） |
| `Jdk14LoggingImpl` | `java.util.logging` | 受（前提是你用 JUL） |
| `NoLoggingImpl` | 没人 | 相当于关掉 |

`mybatis-plus.configuration.log-impl` 这一行，就是在选上面五个里的哪一个。一旦显式写了，MyBatis 就强制用它，不再自动探测。

于是同一条 SQL，走哪个实现，命运完全不同：

```java
StdOutImpl  ──▶  System.out.println  ──▶  stdout  ──▶  到此为止
                 级别、格式、appender 对它全部无效

Slf4jImpl   ──▶  SLF4J  ──▶  logback  ──▶  JSON 文件  ──▶  采集器  ──▶  检索平台
                 级别可关、字段可检索、能进看板和告警
```

| 对比项 | `StdOutImpl` | `Slf4jImpl` |
|:---|:---|:---|
| 输出到哪 | 直接 `System.out` | SLF4J → logback → appender |
| 受日志级别控制 | 不受，永远打 | 受，级别调到 `INFO` 就自动消失 |
| 进不进 JSON 文件 | 不进 | 进，带 `@timestamp` / `logger` / `level` 字段 |
| 能不能被采集进检索平台 | 不能 | 能 |
| 能不能按包名精确开关 | 不能 | 能（`logging.level.xxx.mapper=DEBUG`） |

> ⚠️ <span style="color:red">**这个坑最阴险的地方是"肉眼看不出"：`System.out` 和 logback 的 `ConsoleAppender` 写的是同一个标准输出，终端里 SQL 和其他日志混在一起、格式也像，会以为一切正常。但采集器搬给平台的是 logback 那条路，SQL 根本没上车。**</span>

本项目实测：让请求走一次缓存未命中（必然查库），然后两边对照 ——

```
JSON 文件里含 SQL 的行数 :  0
容器 stdout 里            :  ==>  Preparing: SELECT id,branch_code,...,use_legacy_menu FROM ...
```

## 📊 应用与对比

### 怎么确认管辖边界

> 🔑 **判断某类日志有没有"受管辖"，只问一句：它走不走 SLF4J**。走了，级别能控、能被格式化、能被采集；不走，它就在体系外面自说自话，你所有的日志配置对它统统无效。

三个可以自己动手的检查：

| 想确认什么 | 怎么做 | 预期 |
|:---|:---|:---|
| 日志实现是谁带进来的 | `mvn dependency:tree -Dincludes="ch.qos.logback:*,org.slf4j:*"` | 能看到 `spring-boot-starter-logging` 引出的 logback + slf4j |
| 某个包**实际生效**的级别 | `GET /actuator/loggers/{包名}` | 返回 `{"effectiveLevel":"..."}`；配置写错了这里会如实反映 |
| 某类日志受不受管辖 | 把它的级别降到 `INFO` 以下该级别，看还打不打 | 受管辖会消失；不受管辖照打不误 |

### 本项目做了什么

- `log-impl` 从 `StdOutImpl` 换成 `org.apache.ibatis.logging.slf4j.Slf4jImpl`，让 SQL 日志回到 logback 的管辖范围内
- 把 mapper 包的级别显式写在 `logging.level` 里（生产改 `INFO` 关掉，排查时用 `/actuator/loggers` 运行时打开）
- 排查手法固化下来：**先确认日志的实现链，再动配置文件**

日志怎么分组、怎么输出成 JSON，见 [可观测性-结构化日志](./可观测性-结构化日志.md)；级别怎么选、成本怎么控，见 [可观测性-日志级别与成本控制](./可观测性-日志级别与成本控制.md)。

## 🔥 面试要点

**Q1：为什么有时候日志级别调了不生效？**

> **面试话术**：*"先确认这类日志走不走 SLF4J。Java 的日志是分层的，业务代码调 SLF4J 门面，底下接 logback 实现，配置改的是实现层。但第三方库不一定走这条路，比如 MyBatis 自己定义了一套日志抽象，用 `StdOutImpl` 时直接 `System.out.println`，完全绕过 logback，级别、格式、appender 对它都无效。这种日志还有个隐蔽之处：`System.out` 和 logback 的控制台输出写的是同一个标准输出，肉眼看不出差别，但采集器只搬 logback 那条路，它就丢了。所以排查这类问题，我第一件事是确认日志的实现链，而不是反复改配置文件。"*

**Q2：pom 里没写 logback，它是从哪来的？**

> **面试话术**：*"从 starter 的传递依赖来的。spring-boot-starter-web 会引出 spring-boot-starter-logging，它带来 logback-classic 和 logback-core；slf4j 作为门面也在里面。而 SLF4J 怎么知道该转发给 logback，靠的是 classpath 里 logback-classic 的 META-INF/services 文件 —— SLF4J 2.0 用 ServiceLoader 在运行时扫描，读到就绑定。所以我写的 logback-spring.xml 只是覆盖默认配置，不是启用 logback；就算不写它，日志也照样打。"*

## 🧠 记忆口诀

```
日志分两层：门面管接口，实现管干活

  门面 —— SLF4J 定义 log.info()，自己不输出
  实现 —— logback 判级别、格式化、写文件
  绑定 —— 运行时扫 META-INF/services 自动完成，不写代码

再记一条前提：
  不受管辖的日志，配置对它全是空文
  用日志之前先问一句：它走不走 SLF4J
```

## 🔄 知识闭环

```java
写日志时撞上的两个困惑：
  ① "pom 里没写 logback，它哪来的？"
  ② "级别改了，为什么这条日志不受影响？"
      │
      ▼
① 的答案：分层 + 传递依赖 + 运行时绑定
  业务代码 → SLF4J 门面 → logback 实现 → appender
  starter 把 logback 带进 classpath
  SLF4J 靠 META-INF/services 在运行时找到它
  logback-spring.xml 是覆盖默认配置，不是启用
      │
      ▼
② 的答案：管辖边界
  有的库（如 MyBatis）自己定义日志抽象，不走 SLF4J
  StdOutImpl 直接 System.out，级别、格式、采集全部失效
  换成 Slf4jImpl 才回到管辖范围内
      │
      ▼
出口：先确认管辖边界，再谈日志怎么配。
      受管辖之后，才轮到"输出成什么形态"和"用哪个级别"：
      形态 → 《可观测性-结构化日志》
      级别 → 《可观测性-日志级别与成本控制》
```
