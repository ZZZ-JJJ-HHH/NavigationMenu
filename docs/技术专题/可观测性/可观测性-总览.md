## 📌 一句话核心

> <span style="color:red">**可观测性由日志、指标、链路三根柱子撑起来，三根各回答一类问题，不能互相替代。**</span>

---

## 🎯 背景与问题

### "我打了日志"不等于"我有可观测性"

一个系统只有日志时，能回答"这一次请求发生了什么"，但回答不了"现在整体水位是多少"，也回答不了"这次请求的时间花在哪几段"。

### 三个问题，三类数据

| 你想知道 | 该用哪种数据 |
|:---|:---|
| 这条请求为什么报错？ | 日志 |
| 现在错误率是多少？ | 指标 |
| 这次请求的时间花在哪几段？ | 链路 |

---

## 💡 核心目的

分清三类数据的职责和成本，避免两个常见错误：只做日志就以为够了，或者一开始就上全套。

## ⚙️ 原理与机制

### 三支柱

"可观测性"不是单指日志。它由三根柱子撑起来，三根各回答一类问题：

| 支柱 | 回答什么问题 | 数据量级 | 本项目怎么落 |
|:---|:---|:---|:---|
| **日志 Logs** | 这一次请求到底发生了什么？ | 最大，按条存 | 结构化 JSON + traceId |
| **指标 Metrics** | 现在整体水位是多少？ | 最小，按时间线聚合 | Actuator + Prometheus 端点 |
| **链路 Traces** | 一次请求的时间花在哪几段？ | 中，按 span 存 | 先靠 `chain.step` 的耗时日志，未来可上 OpenTelemetry |

> 🔑 <span style="color:red">**面试常问"日志和指标有什么区别"：日志回答"为什么"，指标回答"多少"。指标告诉你错误率涨了，日志才告诉你那条请求为什么错。两者都要，但如果只能先做一个，先做日志，它能回答的问题更多，是另外两根柱子的原料。**</span>

> ⚠️ **别把"打了日志"和"有可观测性"划等号**。日志只是三根柱子之一，而且是最重的那根，成本和收益都要管起来。

> ⚠️ **还有一个更常见的误解：指标不是从日志里统计出来的。** 两条链路**平行、不共用任何组件**：

```java
日志：应用写日志文件 → 采集器 → 检索平台                      （原始事件，逐条）
指标：应用内存里的计数器 → /actuator/prometheus → Prometheus 拉 → Grafana 画
```

> 🔑 **好记的判据：把日志全关掉，指标照样在涨。** 指标的数字来自框架在代码路径上自动埋的点（那个 `webMvcObservationFilter`），跟你打没打日志毫无关系。删掉日志配置、指标那边一条不少，这是最快的验证方式。

> 🔑 **本质差别在"什么时候聚合"**：指标在**写入时就聚合好了**（每个请求让计数器 +1、耗时累加），所以只有几十条时间线；日志是**原始事件**，每请求一条，要等检索平台事后聚合。这就是两者成本差几个数量级的原因。

> ⚠️ **"从日志里算出指标"这件事确实存在，但不叫 Prometheus**，叫日志指标化（Splunk 的 `timechart`、Loki 的 rate 查询都算）。代价是实时性差、成本高、没法像指标那样做采样控制，所以它能救急，不适合当主路径。

日志这条线怎么搭，见 [可观测性-结构化日志](./可观测性-结构化日志.md) 和 [可观测性-日志采集与Splunk](./可观测性-日志采集与Splunk.md)；日志进入 Splunk 后怎么查，见 [可观测性-Splunk检索入门](./可观测性-Splunk检索入门.md)；完整线上排查案例见 [可观测性-故障排查实战-Redis超时](./可观测性-故障排查实战-Redis超时.md)。

### 深入专题：Actuator 与指标链路

Actuator 负责把应用状态暴露成 HTTP 端点；Micrometer 在应用内存中维护指标；Prometheus 定时拉取并保存时间线。三者职责不同，`health` 正常也不代表业务错误率和延迟正常。

完整机制、端点安全边界、`health`/`metrics`/`prometheus` 的区别、liveness/readiness 和验证命令，见 [可观测性-Actuator与Micrometer](./可观测性-Actuator与Micrometer.md)。

PromQL 语法、指标类型、查询函数和排障查询见 [可观测性-Prometheus查询与可视化](./可观测性-Prometheus查询与可视化.md)。

## 🔥 面试要点

**Q1：日志、指标、链路追踪，你怎么理解它们的区别？**

> **面试话术**：*"三根柱子回答三类问题。日志回答'这一次请求发生了什么'，数据量最大、最细；指标回答'现在整体水位是多少'，是聚合后的时间线，量级最小；链路回答'这次请求的时间花在哪几段'。指标告诉你错误率涨了，日志才告诉你那条请求为什么错，所以两者不能互相替代。如果只能先做一个，我会先做日志，它的信息量最大。"*

**Q2：你怎么知道服务现在是正常的？**

> **面试话术**：*"分三层。最浅的是健康检查端点，判断进程活着、依赖可达；中间是业务指标，比如接口成功率、P95 延迟、缓存命中率；最深是核心业务动作的成功率，比如菜单接口对每个分行都能返回。告警一般挂两个：5 分钟内 5xx 超过 1%，以及 P99 超过阈值。"*

**Q3：liveness 和 readiness 有什么区别？**

> **面试话术**：*"liveness 失败要重启进程，因为进程自己卡死了，重启能救；readiness 失败只是从负载均衡摘掉，不重启，因为依赖还没就绪，重启也没用。两者混用会出大事故，依赖一抖动，所有实例被判 liveness 失败集体重启，反而把故障放大。"*

## 🧠 记忆口诀

```
三根柱子一句话：
  日志说"为什么"，指标说"多少"，链路说"花在哪"

再记两个健康检查：
  liveness 挂了 → 重启
  readiness 挂了 → 摘掉，不重启
```

## 🔄 知识闭环

```java
只做日志的局限：说得清单次请求，说不清整体水位
      │
      ▼
补齐三支柱：
  日志  → 这次请求发生了什么（最重，是另两者的原料）
  指标  → 现在整体多少（最轻，几十条时间线）
  链路  → 时间花在哪几段
      │
      ▼
指标落地：Actuator + Micrometer + Prometheus 端点
健康分组：liveness 重启，readiness 摘流量
告警三要素：阈值 + 通知渠道 + 静默规则
      │
      ▼
出口：日志管"为什么"，指标管"多少"，
      两者配合才能在告警响起时快速回答"坏没坏、为什么坏"。
```
