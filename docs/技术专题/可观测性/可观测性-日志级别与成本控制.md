## 📌 一句话核心

> <span style="color:red">**级别是日志的"精度旋钮"：写代码时定精度（一次性成本），运行时拧旋钮（零成本）。分级的全部价值，就是让这个旋钮真的可用。**</span>

---

## 🎯 背景与问题

### 为什么级别总是混着用

团队里 `INFO` 和 `DEBUG` 混着用、也没人较真，这不奇怪。**在纯文本日志时代，级别混用几乎没有代价**，因为看日志的方式就是 `grep` 一把梭，级别只是个前缀装饰。

成本是看不见的，因为代价藏在两个地方：

- 日志散在几十台机器的文件里，没人会去统计"生产环境的日志里 DEBUG 占多少" —— 那要登几十台机器
- 纯文本没法按字段聚合，"级别分布"这个数字根本算不出来

接进检索平台之后，代价才第一次变得可见：**级别是唯一一个能按成本批量开关的旋钮**。混着用等于把这个旋钮废掉 —— 你没法在生产上"只打开有用那些、只关掉噪音那些"。

### 两种失败模式

| 失败模式 | 表现 | 后果 |
|:---|:---|:---|
| **级别太低** | 所有语句都写成 `log.info` | 闸门只剩"全开"和"全关"两档；要么 40 行噪音，要么连有用的也一起没了 |
| **级别太高** | 细节语句写成 `log.warn` 之类 | 该有的诊断信息不见了，出问题时手里没有证据 |

两种失败模式的共同点是：**旋钮失效**。一个调不动，一个是伪装的。

## 💡 核心目的

让日志同时满足两个相反的要求：

1. **平时不吵**：生产环境的日志量跟请求量同阶，能被检索平台长期承受
2. **需要时能调出细节**：怀疑哪里有问题时，一条命令就能把那一段的中间过程打开

实现手段就是把这两件事**拆到两个不同的成本层**：写代码时定级别（一次性，要走发版），运行时调闸门（零成本，秒级）。

## ⚙️ 原理与机制

### 级别是一道闸门

级别不是"等号"，是**门槛**。闸门只放行**不低于自己**的级别：

```java
严重程度顺序（从高到低）：  ERROR > WARN > INFO > DEBUG > TRACE

闸门设在 INFO：        ERROR ✓   WARN ✓   INFO ✓   DEBUG ✗   TRACE ✗
闸门设在 DEBUG：       ERROR ✓   WARN ✓   INFO ✓   DEBUG ✓   TRACE ✗
```

所以两个必记的结论：

- **把闸门调低，只会让日志变多，不会变少。** 有人以为"设成 DEBUG 就没有 INFO 日志了" —— 正好相反。
- **闸门管不到"身份"在它之上的日志。** 一条写成 `log.info` 的语句，闸门设成 `INFO` 也好、`WARN` 也好，它都在闸门之上，照打不误。

> 🔑 **由此推出分级的目的**：不是"让日志少"，而是**让闸门有中间档**。只有当细节被写在 `DEBUG` 上，它才第一次"落到闸门下面"，你才能在需要的时候单独把它放出来、不需要的时候关回去。

### 五级各管什么

| 级别 | 什么时候用 | 生产开不开 | 一句话判断 |
|:---|:---|:---|:---|
| `ERROR` | 需要人介入的事故 | 开 | 这条日志应该触发告警 |
| `WARN` | 出了意外但能继续（降级、兜底命中、重试成功） | 开 | 该知道，但不该半夜把人叫醒 |
| `INFO` | 关键业务状态变化：请求进出、缓存命中、分流决策 | 开（默认） | 每秒会出现几次？几十次以内可以留 |
| `DEBUG` | 排查用的中间细节：匹配过程、过滤明细、SQL | 关 | 只在"我怀疑这里有问题"时才需要 |
| `TRACE` | 逐条数据的极细粒度 | 关 | 基本是给第三方库准备的 |

### 两条判据

> 🔑 **判据一（数量）：这条日志在生产环境会出现多少次？** 每请求一条的放 `INFO`，每请求几十条的放 `DEBUG`。

> 🔑 **判据二（性质）：它是"决策结果"还是"执行过程"？** 能直接回答业务问题的**决策点**放 `INFO`（命中缓存、分流走了哪条、匹配出几条、过滤掉几条）；**执行骨架和中间细节**放 `DEBUG`（责任链走到第几步、逐条数据的处理过程）。

判据一管数量，判据二管性质，两条都过得了才放心放 `INFO`。

> ⚠️ **一个容易被钻空子的地方**：条数不总是跟请求量走。有的日志条数**跟着数据量走**（比如"每个菜单节点一条"），菜单节点从 25 涨到 250，流量一点没变，日志量翻了十倍。线上"日志量突然暴涨却找不到原因"，根子常常在这里。碰到"每条数据一条日志"的写法，一律按 `DEBUG` 处理。

### 懒加载：级别设对还省 CPU

级别设对省的不只是日志量，还有 CPU。SLF4J 的 `{}` 占位符是**懒加载**的，级别关闭时不会去拼字符串；但写成字符串相加就一定先拼完再丢弃：

```java
log.debug("matched: {}", list);            // ✅ DEBUG 关闭时不拼字符串，开销几乎为零
log.debug("matched: " + list.toString());  // ❌ DEBUG 关闭时也照样拼，白烧 CPU
```

MyBatis 用的就是前一种 —— 它内部先问一句 `isDebugEnabled()`，为 `false` 就直接返回，连 SQL 字符串都不拼。所以"级别设对"和"写法规范"是配套的：级别关掉了，却不小心在参数里做了昂贵的计算，等于白关。

## 📊 应用与对比

### 本项目落成的样子

| 环节 | 级别 | 理由 |
|:---|:---|:---|
| `MenuController` 收到请求 | `INFO` | 请求进入，每请求 1 条 |
| `cache hit` / `cache miss` / `cache set` / `cache evicted` | `INFO` | 决策结果，也是缓存命中率的原始数据 |
| `LegacyCheckHandler` 命中 legacy 分流 | `INFO` | 决策结果：这个分行走了老系统 |
| `LoadMenuHandler` / `FallbackMatchHandler` / `PermissionFilterHandler` / `TreeBuildHandler` 的产出 | `INFO` | 每请求各 1 条，四步决策链的结果 |
| `chain terminated at XxxHandler` | `INFO` | 链在哪一步提前结束，是决策结果 |
| `MenuServiceImpl` 的服务层入口 | `DEBUG` | 和 `MenuController` 打的是同一个 DTO，重复 |
| `chain step: XxxHandler` | `DEBUG` | 每请求 5 条，纯骨架，真正有用的信息在各 Handler 那条里 |
| `LegacyCheckHandler` 未命中 legacy | `DEBUG` | "没走 legacy"是默认情况，绝大多数请求都会打 |
| `MenuTreeBuilder` 的 input / idMap / 逐节点 / roots | `DEBUG` | 算法内部过程，条数跟着**菜单数据量**走而不是请求量 |

> ⚠️ **前提**：这套分级能生效，靠的是所有日志都已经受 SLF4J 管辖。绕过框架的日志（如 MyBatis 的 `StdOutImpl`）分级管不到它 —— 详见 [可观测性-日志框架与管辖边界](./可观测性-日志框架与管辖边界.md)。

### 闸门不同，量差 4 倍

同一份代码、同一次缓存未命中的请求：

| 场景 | 实测行数 |
|:---|:---|
| 闸门 = `INFO` | **8 行** —— 一个能读完的完整请求故事 |
| 同一请求，闸门 = `DEBUG` | **34 行**（8 条 `INFO` 一条没少 + 26 条细节） |
| 缓存命中，闸门 = `INFO` | **2 行** |
| 分级之前（所有语句都是 `log.info`） | **40 行**，闸门怎么调都降不下来 |

那 8 行 INFO 长这样，从"收到请求"到"写入缓存"，每一步都在：

```
00:19:44.121 INFO  getMenuTree, params: MenuQueryDTO(branchCode=SH001, userId=normal_user, ...)
00:19:44.122 INFO  cache miss, key=menu:tree:SH001:normal_user
00:19:44.150 INFO  loaded 25 active menus
00:19:44.151 INFO  after fallback match: 24 nodes
00:19:44.152 INFO  after permission filter: 23 nodes
00:19:44.154 INFO  tree built, root count: 7
00:19:44.154 INFO  chain terminated at TreeBuildHandler
00:19:44.170 INFO  cache set, key=menu:tree:SH001:normal_user, ttl=PT10M
```

### 四种开销控制手段

分级是第一手段，但不是唯一手段。结构化日志不是免费的：JSON 序列化吃 CPU，日志量吃存储和索引额度。高频路径不加控制，会同时拖慢接口和撑爆索引。

| 手段 | 做法 | 注意 |
|:---|:---|:---|
| 分级 | 生产只留 `INFO` 及以上，`DEBUG` 的 SQL 日志只在开发环境开 | 前提是日志都受管辖，否则分级管不住它 |
| 异步写 | 用 `AsyncAppender` 把写盘从业务线程剥离 | 队列要有上限和丢弃策略，否则业务高峰时内存堆积 |
| 采样 | 超高频、低价值的事件按比例采样 | 异常和慢请求必须全量，不能被采样丢掉 |
| 精简字段 | 大对象不进日志，只打节点数、关键 ID | 把整棵菜单树塞进日志，是最常见的体积杀手 |

**开销失控长什么样**（本项目实测）：同一份代码、同样一次启动加一次请求，只把根级别从 `INFO` 换成 `DEBUG`：

| 根级别 | 写进日志文件的行数 | 其中 DEBUG | 其中 INFO |
|:---|:---|:---|:---|
| `INFO` | 几十行 | 0 | 全部 |
| `DEBUG` | 1505 行 | 1449 行 | 一条没少 |

多出来的 1449 行全是框架在自言自语，跟菜单接口没有任何关系：

```
603  org.springframework.beans.factory.support.DefaultListableBeanFactory   创建 bean
408  org.springframework.data.convert.CustomConversions                    类型转换
130  org.apache.catalina.util.LifecycleBase                                Tomcat 生命周期
 37  com.zaxxer.hikari.HikariConfig                                        连接池
```

> ⚠️ **两个必须记住的事实**：第一，`INFO` 的日志在 `DEBUG` 下**一条都没有少** —— 级别是门槛不是等号，调低只会更多、不会更少。第二，多出来的全是噪音，淹掉的正是你要找的那几行。

> 🔑 <span style="color:red">**真正的危害不是"日志变少了"，恰恰是"日志被淹了"。你要的那三五行业务日志，埋在一千五百行 bean 创建记录里。线上排查时你打开的是检索平台，一次查询返回几万条噪音 —— 这比没有日志更难受。分级的目的不是省钱，是让有用的那几行还找得到。**</span>

> 🔑 **判断标准就一句话**：这条日志出问题时你会不会真的去搜它？不会就别打。日志的价值不在多，在"需要的时候搜得到"。

### 运行时调闸门

分级的收益要转化为能力，靠的是"不改代码调闸门"。用 Actuator 的 `loggers` 端点，可以精确到包甚至单个类：

```powershell
# 把某个包临时开到 DEBUG（不重启、不影响其他请求）
curl.exe -X POST http://localhost:8080/actuator/loggers/com.example.navigation_menu.service `
  -H "Content-Type: application/json" -d '{"configuredLevel":"DEBUG"}'

# 查"实际生效"的级别（而不是你写了什么）
curl.exe -s http://localhost:8080/actuator/loggers/com.example.navigation_menu.service

# 撤销运行时覆盖，回到配置文件里的级别
curl.exe -X POST http://localhost:8080/actuator/loggers/com.example.navigation_menu.service `
  -H "Content-Type: application/json" -d '{"configuredLevel":null}'
```

端点的开启方式、安全边界（生产上不要暴露在公网）见 [可观测性-总览](./可观测性-总览.md)。

## 🔥 面试要点

**Q1：日志量太大怎么办？**

> **面试话术**：*"分三层处理。第一是分级，DEBUG 级别的细节只在需要时开，生产默认 INFO；第二是采样，超高频且低价值的事件按比例采样，但异常和慢请求必须全量；第三是保留周期，热数据留 7 到 30 天，更久的转冷存或过期。不过我会先确认一件事：这些日志是不是都分了级。如果所有语句都写成 log.info，那分级这层就是空的，配置怎么调都降不下来。"*

**Q2：你怎么决定一条日志该用 INFO 还是 DEBUG？**

> **面试话术**：*"两条判据。第一条是数量：这条日志在生产环境每秒会出现多少次？每请求一条的放 INFO，每请求几十条的放 DEBUG。第二条是性质：它是决策结果还是执行过程？能直接回答业务问题的那种 —— 命中缓存、走了哪条分流、匹配出几条 —— 放 INFO；执行骨架和中间细节，比如责任链走到第几步、逐条数据的处理过程，放 DEBUG。两条都过得了才放 INFO。"*

**Q3：为什么说级别是"精度旋钮"？**

> **面试话术**：*"因为定级别和调级别是两个成本差几个数量级的事。级别写在代码里，改一次要走发版；闸门可以通过 /actuator/loggers 在运行时改，秒级生效、不用重启。分级的价值就在于把'要不要详细日志'从发版成本降成了命令成本。前提是代码里真的分了级 —— 如果全是 INFO，这个旋钮就只剩全开和全关两档。"*

## 🧠 记忆口诀

```
级别是闸门，不是等号

  调低只多不少 —— DEBUG 下 INFO 一条不少
  闸门管不住上面 —— 写成 info 的，闸门设多高都照打
  闸门要中间档 —— 细节写 DEBUG，才能"需要时放出来"

两条判据定级别：
  数量 —— 每请求几次？几十次的放 DEBUG
  性质 —— 决策结果放 INFO，执行过程放 DEBUG

再记一条红线：
  条数跟着数据走的日志，最危险（菜单从 25 涨到 250，流量没变日志翻十倍）
```

## 🔄 知识闭环

```java
日志量这件事的矛盾：
  平时要少（省成本、不淹没有用信息）
  出问题要多（需要细节才能定位）
      │
      ▼
解法是把两件事拆到两个成本层：
  写代码时定级别    → 一次性成本，要走发版
  运行时调闸门      → 零成本，秒级生效
      │
      ▼
要让闸门有用，代码里必须真的分级：
  判据一（数量）→ 每请求 1 条的 INFO，几十条的 DEBUG
  判据二（性质）→ 决策结果 INFO，执行过程 DEBUG
  实测：8 行 / 34 行 / 2 行，分级前是 40 行且降不下来
      │
      ▼
前面还有一道前提：
  所有日志都得受 SLF4J 管辖 —— 见《可观测性-日志框架与管辖边界》
      │
      ▼
出口：平时 INFO 只留决策链，出问题时一条命令把细节放出来，
      查完关回去。日志才既便宜、又够用。
```
