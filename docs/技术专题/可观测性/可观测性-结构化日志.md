## 📌 一句话核心

> <span style="color:red">**结构化日志 = 一条日志一个 JSON 对象，字段名固定下来，机器就能按字段检索、聚合、告警。**</span>

---

## 🎯 背景与问题

### 纯文本日志长什么样

项目里现在的日志语句：

```java
log.info("cache hit, key={}", key);
```

输出：

```
17:04:19.880 [http-nio-8080-exec-1] INFO  c.e.n.s.cache.MenuTreeCacheService - cache hit, key=menu:tree:SH001:normal_user
```

人读没问题。但一旦要回答"缓存命中率是多少"，问题就出来了。

### 核心痛点

| 痛点 | 表现 |
|:---|:---|
| 只能全文搜 | 想按 `branchCode=SH001` 过滤，只能拿字符串去猜，容易误伤 |
| 没法聚合 | 算 QPS、P95、错误率要先写正则把字段抠出来，脆弱且慢 |
| 格式随人写 | 同一个人今天写 `cache hit`，明天写 `cacheHit`，看板对不上 |
| 字段名混乱 | `costMs` / `elapsed` / `duration` 三种写法混用，聚合不出来 |
| 敏感信息裸奔 | 顺手把 userId、卡号打进 message，审计过不了 |

> ⚠️ **关键认知**：日志的消费者不止是人，还有检索平台、看板和告警规则。**为机器设计的日志，人才最容易用。**

---

## 💡 核心目的

让一条日志同时满足两个条件：

1. **人看得懂**：本地开发时一眼能看出发生了什么
2. **机器认得出来**：检索平台能按字段过滤、聚合、画图、告警

手段就是"同一个日志事件，两种输出形态"。

## ⚙️ 原理与机制

### 一条日志是怎么产生的

`pom.xml` 加个依赖、`logback-spring.xml` 写段配置，到底在做什么？先把四个角色分清。

| 角色 | 是什么 | 本项目里的对应物 | 职责 |
|:---|:---|:---|:---|
| 门面 API | SLF4J | `@Slf4j` 生成的那个 `log` 变量 | 你写的 `log.info()` 调的就是它 |
| 实现 | logback | Spring Boot 默认带的 `ch.qos.logback` | 真正干活 |
| 日志对象 | `ILoggingEvent` | logback 运行时内部创建 | 承载一次日志调用的全部信息 |
| 输出组件 | Appender + Encoder | `ConsoleAppender`、`RollingFileAppender`、`LogstashEncoder` | 决定输出到哪、输出成什么格式 |

`log.info("cache hit, key={}", key)` 这一行执行时，并不是直接拼字符串输出。logback 会先造一个对象，把这次调用的所有信息装进去：

```java
// 概念示意，不是真实源码
ILoggingEvent event = new LoggingEvent(
    timestamp,    // 17:04:19.880
    level,        // INFO
    loggerName,   // c.e.n.s.cache.MenuTreeCacheService
    threadName,   // http-nio-8080-exec-1
    message,      // "cache hit, key=menu:tree:SH001:normal_user"
    mdcMap,       // {traceId = 7f3a9c21e5b04d8a}
    throwable     // 异常堆栈，没有就是 null
);
```

这个 `ILoggingEvent` 就是"日志对象"。它是**内存里的临时对象，一次日志调用一个**，不是文件，也不需要你写任何类。业务代码里找不到它，是正常的。

> 🔑 **Encoder 是翻译器**：Appender 决定"输出到哪"，Encoder 决定"输出成什么格式"。同一个日志对象交给不同的 encoder，就变成不同形态。

```java
log.info(...)  →  ILoggingEvent  →  Encoder  →  Console / File
                   （日志对象）      （翻译）      （落地）
```

| Encoder | 输出形态 | 本项目用在哪 |
|:---|:---|:---|
| `PatternLayoutEncoder` | `%d %-5level %logger - %msg%n` 拼成一行纯文本 | `CONSOLE` appender，给人看 |
| `LogstashEncoder` | 把对象里的字段拍平成一行 JSON | `JSON_FILE` appender，给采集器读 |

> 🔑 **`logstash-logback-encoder` 加的不是采集能力，是一个翻译器实现**。它不采集、不传输，唯一职责是把 `ILoggingEvent` 翻译成 JSON。不加这个依赖，配置里那句 `class="net.logstash.logback.encoder.LogstashEncoder"` 会在启动时直接抛 `ClassNotFoundException`。

同一次 `cache hit`，两个 encoder 各翻译一次，内容一样、形态不同：

```
# CONSOLE 出来的（纯文本）
17:04:19.880 [http-nio-8080-exec-1] INFO  c.e.n.s.cache.MenuTreeCacheService - cache hit, key=menu:tree:SH001:normal_user
```

```json
{"@timestamp":"2026-10-16T09:04:19.880Z","message":"cache hit, key=menu:tree:SH001:normal_user","logger":"c.e.n.s.cache.MenuTreeCacheService","thread":"http-nio-8080-exec-1","level":"INFO","service":"navigation-menu"}
```

其中 `service` 来自配置里的 `<customFields>{"service":"navigation-menu"}</customFields>`。等 `TraceIdFilter` 接上之后，MDC 里的 `traceId` 会自动变成 JSON 的一个顶层字段：

```json
{"@timestamp":"...","traceId":"7f3a9c21e5b04d8a","message":"cache hit, ..."}
```

> 🔑 **这就是 MDC 的价值所在**：MDC 里的值会被 encoder 自动取出来拍进 JSON，完全不用在 `log.info()` 里手拼。手拼的话，traceId 只是 `message` 里的一段文本，检索平台没法把它当字段过滤聚合。详见 [可观测性-链路追踪与MDC](./可观测性-链路追踪与MDC.md)。

### MDC → JSON 字段的完整链路（traceId 为例）

上面那段只说了"MDC 的值会进 JSON"，但没说**怎么进的**。这个机制值得单独拆一遍，因为它同时串起了三个完全独立的环节，缺任何一个都不行。

`net.logstash.logback.encoder.LogstashEncoder` 这个类有一个默认行为：**扫一遍当前线程的 MDC（就是 `getMDCPropertyMap()` 那个 Map），把里面所有的 key-value 都序列化成 JSON 的顶层字段**，key 原样保留，value 原样写入。`traceId` 恰好就是最典型的例子。

完整链路：

```
TraceIdFilter.doFilterInternal()
  │
  │  ① resolveTraceId() → 决定 ID（traceparent 复用 / X-Trace-Id 复用 / 自己生成 UUID）
  │  ② MDC.put("traceId", "956c022ea51e4f44885caa7eaf6c6a41")
  │     → 放进 ThreadLocal Map，当前线程之后所有代码无需感知
  │
  ▼
AccessLogFilter / Controller / Service 里任何一处 log.info(...)
  │  业务代码零改动，它根本不知道 traceId 存在
  │
  ▼
Logback 内部造出 ILoggingEvent
  │  getMDCPropertyMap() 懒加载时把当前线程的 MDC 快照装进去
  │
  ▼
LogstashEncoder 开始序列化
  │  调用 MdcJsonProvider → 读 event.getMDCPropertyMap() → 发现 traceId
  │  自动加一个顶层字段："traceId": "956c022ea51e4f44885caa7eaf6c6a41"
  │
  ▼
app.log 里那行 JSON 就带上了 traceId
```

对照 `TraceIdFilter`（`src/main/java/com/example/navigation_menu/filter/TraceIdFilter.java`）的源码，就是这几行：

```java
String traceId = resolveTraceId(request);   // 决定 ID
MDC.put(MDC_KEY, traceId);                  // ← 关键这一行
try {
    chain.doFilter(request, response);       // 放行，后面所有代码都在这个线程里跑
} finally {
    MDC.remove(MDC_KEY);                    // 线程要回池，必须清
}
```

> 🔑 **MDC 是唯一的交接点**。Filter 写一次，Encoder 读一次，业务代码全程零感知。这也是为什么 `AccessLogFilter` 里的 `log.info("access, ...")` 完全没提 traceId，但 JSON 里却有 —— 它根本不需要提。

### 两条输出通道怎么各取所需

同一次 `log.info()`，CONSOLE 和 JSON_FILE 走的是**完全不同的取 traceId 方式**：

| 通道 | Encoder | 怎么拿到 traceId | 代码在哪控制 |
|:---|:---|:---|:---|
| CONSOLE | `PatternLayoutEncoder` | 靠 pattern 里写 `[%X{traceId:--}]` —— 显式声明"我要这个" | `logback-spring.xml` 的 `<pattern>` |
| JSON_FILE | `LogstashEncoder` | 自动扫 MDC —— 默认行为，不需要配 | 不用配 |

这就是为什么 `logback-spring.xml` 里只给 CONSOLE 加了 `[%X{traceId:--}]`，JSON 那路 `<LogstashEncoder>` 里**一个 traceId 相关的字都没写**——它白送。

`%X{traceId:--}` 里的 `:--` 是默认值：如果 MDC 里没放 traceId（服务启动时的日志、定时任务还没进 Filter 的日志），就显示 `--` 而不是空括号，视觉上一眼能看出这条日志属于"请求之外"。

> ⚠️ **反过来想也成立**：如果将来不想让某个 MDC 字段出现在 JSON 里，就不能用 LogstashEncoder 的默认行为 —— 要改用 `includeMdc` / `excludeMdcKeys` 之类的配置显式排除它。同理，CONSOLE 那路你 pattern 里不写 `%X{userName}`，就算 MDC 里放了 userName，控制台也看不到。

依赖和配置是两件事：`pom.xml` 加依赖是把翻译器的 jar 放进 classpath，`logback-spring.xml` 写 encoder 类名是告诉 logback 用哪个翻译器。

> ⚠️ **缺一不可**：只加依赖不写配置，等于工具买回来不用；只写配置不加依赖，启动直接崩。

### 源码级：每个字段是谁写进去的

上面那张 `ILoggingEvent` 示意图是概念版。真实情况是：**这个对象里没有几个值是在构造函数里就填好的**，很多字段是懒加载 —— 第一次有人读它时才去取。把这条看清，JSON 里每个字段的出处就全对上了。

下面这些方法和字段名，都来自你本机 `~/.m2` 里那份 `logback-classic` 的字节码。

**第一步：`log.info()` 时造对象的构造函数只收 6 个参数**

```java
// ch.qos.logback.classic.spi.LoggingEvent
LoggingEvent(String fqcnOfLoggerClass, Logger logger, Level level,
             String message, Throwable throwable, Object[] argArray)
```

注意**没有线程名，也没有时间戳**。构造函数内部做这几件事：

```java
this.loggerName    = logger.getName();        // → JSON 的 logger
this.level         = level;                   // → JSON 的 level
this.message       = message;                 // → JSON 的 message（只是模板原文）
this.argumentArray = argArray;                // → 你传的那一堆参数，kv 就在里面
Instant now = Clock.systemUTC().instant();    // → JSON 的 @timestamp 的来源
initTmestampFields(now);                      //   timeStamp = epochSecond*1000 + nano/1e6
if (throwable != null) this.throwableProxy = new ThrowableProxy(throwable);  // → stackTrace
```

**第二步：三个字段是懒加载的**

```java
public String getThreadName() {                  // → JSON 的 thread
    if (threadName == null) {
        threadName = extractThreadName(Thread.currentThread());
    }
    return threadName;
}

public Map<String, String> getMDCPropertyMap() {  // → JSON 的 traceId
    if (mdcPropertyMap == null) {
        MDCAdapter mdc = loggerContext.getMDCAdapter();   // 运行时是 LogbackMDCAdapter
        mdcPropertyMap = mdc.getPropertyMap();            // 就是 ThreadLocal 里那个 Map
    }
    return mdcPropertyMap;
}

public String getFormattedMessage() {             // → JSON 的 message
    if (formattedMessage == null) {
        formattedMessage = MessageFormatter
                .arrayFormat(message, argumentArray).getMessage();   // SLF4J 的格式化器
    }
    return formattedMessage;
}
```

三行分别回答三个"它怎么来的"：`thread` 是 `Thread.currentThread().getName()`；`traceId` 是 `TraceIdFilter` 写进 MDC 的那个值；`message` 里的 `{}` 不是 logback 换的，是 **SLF4J 的 `MessageFormatter.arrayFormat()`** 换的。

**第三步：两个 appender 翻译的是同一个对象**

一次 `log.info()` 只造**一个** `LoggingEvent`，然后 `callAppenders(event)` 把它发给所有 appender。你的配置里有两个，所以两边拿到的数据一模一样，差别只在 encoder：

| 输出去哪 | Encoder | 怎么从对象变成文本 |
|:---|:---|:---|
| `CONSOLE` | `PatternLayoutEncoder` | 只渲染你 pattern 里写了的那几个字段，没写的扔 |
| `JSON_FILE` | `LogstashEncoder` | 交给一串 provider，每个 provider 负责一个字段 |

**第四步：JSON 每个字段对应哪个 provider**

| JSON 字段 | 谁写的（Provider 类） | 从 event 的哪个方法取 | 你在哪儿控的 |
|:---|:---|:---|:---|
| `@timestamp` | `LoggingEventFormattedTimestampJsonProvider` | `getInstant()` | `<timeZone>UTC</timeZone>` |
| `message` | `MessageJsonProvider` | `getFormattedMessage()` | `log.info()` 的 `{}` 模板与参数 |
| `logger` | `LoggerNameJsonProvider` | `getLoggerName()` | `@Slf4j` 标在哪个类上 |
| `thread` | `ThreadNameJsonProvider` | `getThreadName()` | 运行时线程，代码里不用管 |
| `level` | `LogLevelJsonProvider` | `getLevel()` | 写 `log.info` 还是 `log.debug` |
| `traceId` | `MdcJsonProvider` | `getMDCPropertyMap()` | `TraceIdFilter` 里的 `MDC.put` |
| `eventType` `method` `path` `status` `durationMs` `clientIp` | `ArgumentsJsonProvider` | `getArgumentArray()` | `AccessLogFilter` 里的 `kv(...)` |
| `service` | `GlobalCustomFieldsJsonProvider` | 不看 event，纯静态 | `logback-spring.xml` 的 `<customFields>` |
| `stackTrace` | `StackTraceJsonProvider` | `getThrowableProxy()` | 有没有抛异常；`fieldNames` 把默认的 `stack_trace` 改成了 `stackTrace` |

这串 provider 都是 `logstash-logback-encoder` jar 里真实存在的类，都能在 `net/logstash/logback/composite/loggingevent/` 这个包下找到（`MdcJsonProvider`、`ArgumentsJsonProvider`、`StackTraceJsonProvider` …）。

> 🔑 **这张表顺手解释了一个容易混的地方**：`traceId` 和 `eventType` 那批字段走的是**两条完全不同的路**。`traceId` 来自 `getMDCPropertyMap()`（MDC 这条链），`eventType` 那批来自 `getArgumentArray()`（你传的参数这条链）。所以"加个字段"没有统一的做法 —— 看它是**这次请求的上下文**（放 MDC）还是**这一次调用专有的数据**（当参数传）。

**第五步：一个意外收获 —— `prepareForDeferredProcessing()`**

同一段字节码里还有这个方法：

```java
public void prepareForDeferredProcessing() {
    getFormattedMessage();   // 强制求值
    getThreadName();         // 强制求值
    getMDCPropertyMap();     // 强制求值
}
```

logback 的**异步 appender** 在把事件丢进队列之前会调它，目的就一个：把这些懒加载的值先"凝固"到对象上。原因很直白 —— 异步线程不是原来的线程，`Thread.currentThread()` 和 MDC 的 ThreadLocal 都拿不到原值了。这就是"异步链路丢 traceId"那个坑的**源码出处**，也解释了为什么 logback 敢在异步场景下继续用 MDC。

**自己验一遍**：上面每个方法名都能在你本机的 jar 里翻出来。

```powershell
javap -p -c -cp "$env:USERPROFILE\.m2\repository\ch\qos\logback\logback-classic\1.5.38\logback-classic-1.5.38.jar" `
  ch.qos.logback.classic.spi.LoggingEvent
```

### 拿到一条日志，先看它是谁打的

字段的出处搞清了，还剩一个更实际的问题：日志文件里那么多行，**哪些是自己代码打的，哪些是框架在自言自语？**

判据只有一个：**看 `logger` 字段**。它就是产出这条日志的类名，谁调的 `LoggerFactory.getLogger(...)` 就写谁。

```
logger = com.example.navigation_menu.filter.AccessLogFilter   →  你写的
logger = org.springframework.web.servlet.DispatcherServlet     →  Spring 打的
logger = org.hibernate.validator.internal.util.Version         →  第三方库打的
```

规则很朴素：**拿 `logger` 跟自己的包名前缀比一比**（本项目是 `com.example.navigation_menu`）。对得上，这行日志受你的规范约束，字段、级别、内容都该由你负责；对不上，那是框架按自己的习惯在说自己的事，你改代码改不到它，只能调它的级别或者干脆别管。

**看一个真实数字。** 本地跑一轮之后，`logs/app.log` 一共 57 行，按 `logger` 分组是这样的：

```
6   com.example.navigation_menu.NavigationMenu                ← 启动横幅
6   ...data.repository.config.RepositoryConfigurationDelegate  ← Spring Data
5   com.example.navigation_menu.filter.AccessLogFilter         ← 访问日志（本次新增）
4   org.springframework.web.servlet.DispatcherServlet
4   org.apache.catalina.core.ContainerBase.[Tomcat].[localhost].[/]
4   org.springframework.boot.web.embedded.tomcat.TomcatWebServer
2   com.example.navigation_menu.controller.MenuController      ← 自己的
2   com.example.navigation_menu.exception.GlobalExceptionHandler
2   org.hibernate.validator.internal.util.Version              ← 第三方库
...
```

> 🔑 **57 行里真正属于业务的只有个位数，其余全是框架的启动日志。** 所以"这份日志我读不懂"是正常的 —— 读不懂的那些本来就不需要你读。排查时该做的是按 `logger` 过滤出自己那几个包，而不是从头往下翻。

> ⚠️ **第三方日志量大了也不要硬看，要调它的级别**。它们不受你的代码规范约束，但受你的配置约束：

```yaml
logging:
  level:
    # 框架启动噪音只想在排障时看，平时压到 WARN
    org.springframework.data.repository.config: WARN
    org.apache.catalina: WARN
```

> 🔑 **一句话记法**：`logger` 字段是这条日志的"门牌号"。先按门牌号分清是谁家的事，再决定是改代码（自己家）、调级别（别人家），还是直接跳过（不用管）。

### 想深入：日志从哪来、谁在管

本章只讨论“如何设计结构化日志”。SLF4J、Logback、`logback-spring.xml`、MyBatis `StdOutImpl` 为什么绕过 Logback，以及日志管辖边界，属于独立的框架专题：

[可观测性-日志框架与管辖边界](./可观测性-日志框架与管辖边界.md)

### 日志分三类

| 类型 | 写给谁 | 频率 | 内容 |
|:---|:---|:---|:---|
| **访问日志** | 运维 / 监控 | 每请求一条 | method、path、状态码、耗时、traceId、调用方 |
| **业务日志** | 业务方 / 研发 | 关键决策点 | 缓存命中、匹配结果、过滤结果、分流开关 |
| **异常日志** | 研发 | 出错时 | 异常类型、堆栈、上下文参数 |

> 🔑 三类日志的**字段规范是同一套**。这样在检索平台里可以用一条查询，把一次请求的三类日志全部串出来。

## 📊 应用与对比

### 日志字段设计

字段设计决定后面能不能搜。建议分五组固定下来：

| 分组 | 字段 | 说明 |
|:---|:---|:---|
| 通用 | `@timestamp` `level` `logger` `thread` `service` `env` | 日志框架自带，`service` / `env` 用于区分多服务多环境 |
| 追踪 | `traceId` | 一个请求一个，跨系统传递的核心 |
| HTTP | `method` `path` `status` `durationMs` `clientIp` | 访问日志的主干字段 |
| 业务 | `eventType` `countryCode` `entityCode` `channelCode` `branchCode` `userId` | 本项目特有的维度，排查业务问题全靠它们 |
| 异常 | `errorType` `errorCode` `stackTrace` | 便于按错误类型聚合 |

> 🔑 **字段命名要固定，同一含义不能有两种写法**。`durationMs` 就是 `durationMs`，不要一会儿 `costMs`、一会儿 `elapsed`。字段名一乱，看板就废了。

> ⚠️ **脱敏红线**：`userId`、卡号、手机号、证件号属于敏感字段。银行场景要么脱敏落盘（如 `U***1234`），要么只落哈希，绝不能原样进日志平台。

### eventType 事件字典

字段名定下来了，取值也要定。否则同一个事件你今天叫 `cache_hit`、明天叫 `cacheHit`，看板就聚合不出来。建议固定成一张表：

| eventType | 触发点 | 关键字段 | 能回答的问题 |
|:---|:---|:---|:---|
| `access` | 每次请求结束 | `method` `path` `status` `durationMs` `clientIp` | QPS、错误率、P95 / P99 |
| `chain.step` | 每个 Handler 执行前后 | `handler` `order` `costMs` | 慢在哪一步 |
| `cache` | 缓存的 get / put | `result`（hit / miss / set）`key` `ttl` | 缓存命中率 |
| `fallback.match` | 四维匹配完成 | `matched` `exact` `wildcard` | 为什么这条菜单匹配上 / 没匹配上 |
| `permission.filter` | 权限过滤完成 | `before` `after` `cut` | 权限砍掉了几个节点 |
| `legacy.shortcut` | Legacy 分流命中 | `branchCode` `useLegacy` | 还有多少分行留在旧系统 |

**这张表已经落地了（第 4 步）。** 实测一条冷请求（`traceId=step4-demo-001`），同一次请求里留下的是这些独立字段：

```json
{"eventType":"fallback.match","candidates":24,"matched":24,"exact":1,"wildcard":23,"nodeIds":["transfer-cross","mine","card-point","product",...]}
{"eventType":"permission.filter","decision":"deny","nodeId":"luxury","requiredPerm":"LUXURY_CARD"}
{"eventType":"permission.filter","before":24,"after":23,"cut":1,"cutNodeIds":["luxury"],"userPerms":[]}
{"eventType":"legacy.shortcut","branchCode":"SH001","useLegacy":false,"branchFound":true}
{"eventType":"cache","result":"miss","key":"menu:tree:SH001:normal_user"}
{"eventType":"cache","result":"set","key":"menu:tree:SH001:normal_user","ttl":"PT10M"}
```

注意这里有**一条汇总 + 一条明细**的分工：`permission.filter` 的汇总是 `before=24, after=23, cut=1`，明细是"哪一个被砍、缺哪个权限"。汇总回答"砍了几个"，明细回答"砍了谁、为什么"。

> 🔑 **这就是"结构化"和"打印一行字"的分水岭**：`nodeId=luxury` 现在是**字段**，可以按它精确过滤；换成 `"砍掉了 luxury，因为缺 LUXURY_CARD"` 这句话，就只能全文搜索，还可能把用户名叫 luxury 的记录一起搜出来。字段是给机器做等值匹配的，句子是给人读的 —— 两者要同时存在，但各走各的通道。

> 🔑 **有了这张表，排查就变成"按顺序拼一次请求的故事"**：`access` 是开头（这次请求是谁、花了多久），`chain.step` 是过程，`cache` / `fallback.match` / `permission.filter` 是中间的决策细节。一条查询按时间排一遍，整个判断过程就还原出来了。

> ⚠️ **命名约定要统一**：`eventType` 用点号分层（`chain.step`），普通字段用驼峰（`costMs`）。点号分层的好处是能通配，搜 `eventType=chain.*` 就是全部链路步骤，将来加了 `chain.skip` 也不用改查询。

### 本项目的落地配置

`logback-spring.xml` 里挂了两个 appender，同一个 `log.info()` 同时落到两边：

```java
root
 ├─ CONSOLE   → PatternLayoutEncoder  → stdout，给人看
 └─ JSON_FILE → LogstashEncoder       → /app/logs/app.log，给采集器读
```

JSON 那一路还做了三件事：用 `<timeZone>UTC</timeZone>` 统一时区、用 `<customFields>` 打上 `service` 标签、用 `<fieldNames>` 把字段名对齐到上面那张字段表。

> ⚠️ **动手前先改一个坑**：`application.yaml` 里 `mybatis-plus.configuration.log-impl` 原来是 `StdOutImpl`，它绕过 logback 直接把 SQL 打到标准输出，既没有 traceId，又是日志量的黑洞。要改成 `org.apache.ibatis.logging.slf4j.Slf4jImpl`，并把级别降到 DEBUG，生产环境关掉。原理见 [可观测性-日志框架与管辖边界](./可观测性-日志框架与管辖边界.md)。

文件落在哪、权限归谁，见 [可观测性-Docker容器与日志落盘](./可观测性-Docker容器与日志落盘.md)。

## 🔥 面试要点

**Q1：为什么要用 JSON 日志，纯文本不行吗？**

> **面试话术**：*"纯文本是给人看的，检索平台拿到之后只能全文匹配。JSON 每个字段都是独立的，可以直接按字段过滤、聚合、画图。比如要看某个分行的 P99 延迟，纯文本得先写正则把字段抠出来，JSON 直接 stats 就行。所以我一般两条输出都留着，本地开发看控制台，生产环境走 JSON 给采集器。"*

**Q2：日志字段应该怎么设计？**

> **面试话术**：*"按排查时会用到的维度来切。通用字段交给框架，追踪字段放 traceId，HTTP 字段放 method/path/status/durationMs，业务维度放这个系统特有的那几个。关键是字段名要固定，同一含义不能有两种写法，否则看板写完还得回头改。"*

> 💡 另外两个高频问题在各自专题里：**"日志量太大怎么办"** 见 [可观测性-日志级别与成本控制](./可观测性-日志级别与成本控制.md)，**"为什么日志级别调了不生效"** 见 [可观测性-日志框架与管辖边界](./可观测性-日志框架与管辖边界.md)。

## ✅ 本步小结

这一节把"第一步做了什么"固化成结论 —— 过一段时间回头看这一段就够了。

**目标**：让日志从"一行给人读的文本"变成"一行给机器读的数据"，并且平时不吵、需要时能把细节调出来。

**做了三件事**

| # | 做了什么 | 为什么这么做 |
|:---|:---|:---|
| 1 | **日志结构化**：加 `logstash-logback-encoder`，写 `logback-spring.xml`；同一句 `log.info()` 同时落成两种形态 —— 控制台文本给人看、JSON 文件给机器读。每条 JSON 带固定字段 `@timestamp` / `level` / `logger` / `thread` / `service` | JSON 只是**载体**，**固定字段才是价值**：有字段才能按字段过滤、聚合、画图、告警；纯文本只能全文匹配。所以"结构化"不等于"写成文件"，写文件只是落点 |
| 2 | **日志分级**：逐条判断代码里每条语句该放 `INFO` 还是 `DEBUG`（两条判据见 [可观测性-日志级别与成本控制](./可观测性-日志级别与成本控制.md)） | 让**级别闸门**真正可用。改代码定级别是一次性成本，运行时调闸门是零成本；"合理分级"是手段，**让闸门有用**才是目的。如果全都写成 `INFO`，闸门就只剩"全开"和"全关"两档 |
| 3 | **打通管辖**：把 `mybatis-plus.configuration.log-impl` 从 `StdOutImpl` 换成 `Slf4jImpl` | `StdOutImpl` 直接 `System.out`，**绕过 logback** —— 这类日志既不受级别控制，也进不了 JSON 文件，等于在体系外自说自话。要先确认"所有日志都受管辖"，分级才有意义 |

**怎么验证这一步真的做到了**

```powershell
# ① JSON 是不是真的在写
curl.exe -s -X POST http://localhost:8080/api/menu/tree -H "Content-Type: application/json" -d "@test/test_body.json"
Get-Content logs\app.log -Tail 3

# ② 级别是不是真的生效（看"实际生效"，不是看"你写了什么"）
curl.exe -s http://localhost:8080/actuator/loggers/com.example.navigation_menu.mapper

# ③ 闸门是不是真的能开能关
curl.exe -X POST http://localhost:8080/actuator/loggers/com.example.navigation_menu -H "Content-Type: application/json" -d '{"configuredLevel":"DEBUG"}'
curl.exe -X POST http://localhost:8080/actuator/loggers/com.example.navigation_menu -H "Content-Type: application/json" -d '{"configuredLevel":null}'
```

| 场景 | 实测行数 |
|:---|:---|
| 缓存未命中，闸门 = `INFO` | **8 行** —— 一个能读完的完整请求故事 |
| 同一请求，闸门 = `DEBUG` | **34 行**（8 条 `INFO` 一条没少 + 26 条细节） |
| 缓存命中，闸门 = `INFO` | **2 行** |
| 分级之前（所有语句都是 `log.info`） | **40 行**，闸门怎么调都降不下来 |

> 🔑 <span style="color:red">**一句话结论：这一步解决的是"日志能不能被机器读"；"日志够不够解问题"是下一步（业务埋点）的事。两道门槛都过了，日志才真的能当排查工具用。**</span>

**这一步没做什么**（留给后面）

- 日志之间仍然只靠"时间先后"关联，**没有 traceId** —— 并发一上来，就分不清哪几行属于同一次请求 **（第 2 步已补：`TraceIdFilter` + MDC）**
- 细节日志还没有**业务字段**（匹配到哪几条配置、砍掉哪几个节点）—— 现在只报了数量 **（第 4 步已补：`fallback.match` / `permission.filter` / `legacy.shortcut` / `cache` 四类事件）**
- 日志还只在本地文件里，**没有采集进检索平台** **（第 5 步待做）**
