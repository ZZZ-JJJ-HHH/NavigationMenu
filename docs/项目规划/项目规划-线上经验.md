## 📌 一句话核心

> <span style="color:red">**线上经验 = 出问题能定位、流量大小能看见、变更上线能控制。它不要求你进过大厂，要求你能说清一套闭环。**</span>

## 🎯 背景与问题

### 面试官怎么探"线上经验"的底

面试官不会直接问"你有线上经验吗"。他会问一些只有真干过才答得顺的问题：

| 面试官的问法 | 他真正想确认的 |
|:---|:---|
| "线上接口突然变慢，你怎么查？" | 有没有可检索的日志和延迟指标，知不知道从哪一层开始切 |
| "你怎么判断服务现在是不是正常的？" | 有没有监控看板、有没有告警，阈值怎么定 |
| "发布完出问题怎么办？" | 有没有回滚手段，能不能定位到是哪次变更引入的 |
| "一个用户说他的菜单不对，你怎么排查？" | 能不能把业务问题映射到日志里的字段 |
| "日志量太大了怎么办？" | 知不知道分级、采样、成本 |
| "你遇到过最难的线上问题是什么？" | 有没有一手经历，有没有复盘能力 |

> ⚠️ **这六个问题，没有一条要求你在正编岗位待过**。它们要的是你亲手搭过一次、踩过一次，能讲出取舍。

### "我只是个外包"

先摆正一件事：**外包身份限制的是权限和视角，不是你和真实环境的距离。**

你在汇丰的环境里待过，这件事本身就是资产。之所以"感觉自己不了解"，通常是三个原因：

| 原因 | 具体表现 |
|:---|:---|
| 没人讲"为什么" | 你拿到的是 ticket，不是问题背景 |
| 只看一小块 | 只被允许碰自己那个模块，看不到全貌 |
| 事故时不在场 | 排查会议里没有你 |

> 🔑 **但你"看到过"的东西都是真材料**：工单模板里的日志链接、报错信息里的 trace id、运维排查时打开的页面、发版前后固定的动作、上线前的检查单。你现在觉得这些"跟我没关系"，面试时它们就是"我进过真实线上环境"的证据。

### 通用规律 vs 汇丰具体情况

本文档写的是**大型企业通用的工程做法**，不是汇丰内部资料。两者要分清：

| 分类 | 内容 |
|:---|:---|
| **可以放心引用的通用规律** | 结构化日志、请求级唯一 ID 贯穿、日志集中检索、看板告警、敏感字段脱敏 |
| **我不知道、不要替它下结论的** | 汇丰具体用哪个平台（Splunk / ELK / 自研）、内部索引和权限怎么划分 |

> ⚠️ 面试时把通用规律说成"我在汇丰见过"是危险的。说"行业通用做法是这样，我在汇丰接触到的是其中哪一部分"才站得住。

## 💡 核心目的

补这块能力，目标不是背名词，而是能对三个问题给出具体答案：

1. **定位**：线上出问题，我怎么在几分钟内找到是哪个请求、卡在哪一层？
2. **度量**：现在有多少流量、成功率多少、慢在哪里？
3. **恢复**：哪次变更引入的问题，怎么快速回退？

> 🔑 这三个问题，正好对应可观测性、发布变更、故障处理三块能力。

## ⚙️ 原理与机制

### 线上经验的四个能力块

```java
                      ┌──────────┐
                      │ 线上经验  │
                      └────┬─────┘
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
    ┌──────────┐     ┌──────────┐     ┌──────────┐
    │ 可观测性  │     │ 发布变更  │     │ 故障处理  │
    │ 日志      │     │ 流水线    │     │ 定位      │
    │ 指标      │     │ 灰度      │     │ 止血      │
    │ 告警看板  │     │ 回滚      │     │ 复盘      │
    └──────────┘     └──────────┘     └──────────┘
          │                │                │
          └────────────────┴────────────────┘
                           ▼
                     ┌──────────┐
                     │  合规     │
                     │ 脱敏      │
                     │ 审计      │
                     │ 保留周期  │
                     └──────────┘
```

> 🔑 这四块里，**可观测性是地基**。没有日志和指标，故障处理只能靠猜，发布也不敢快。每一块的实现细节见下一节的专题索引。

### 一次线上故障的标准处理流程

```java
告警响了 / 用户反馈
      │
      ▼
① 确认影响面 ── 多少人、哪些分行、持续多久
      │
      ▼
② 止血优先 ──── 先恢复，再找根因
      │          手段：回滚 / 切开关 / 限流 / 重启
      ▼
③ 定位根因 ──── 用 traceId 拉出当事请求的全链路
      │          看耗时段、异常堆栈、变更时间点
      ▼
④ 验证恢复 ──── 看板和告警回到正常水位
      │
      ▼
⑤ 复盘 ──────── 为什么没挡住、告警为什么没提前
```

> ⚠️ <span style="color:red">**顺序不能错：先止血再定位。这是线上和实验室最大的区别，也是面试最容易露怯的地方。**</span>

## 📊 应用与对比

### 能力块 → 本项目的落地动作

把上面每一块能力，翻译成这个项目里具体要动的代码和配置：

| 能力 | 现状 | 要做什么 | 主要落点 |
|:---|:---|:---|:---|
| 结构化日志 | `@Slf4j` 打纯文本 | 换 JSON 编码器，一行一个 JSON | 新增 `logback-spring.xml`，`pom.xml` 加 `logstash-logback-encoder` |
| 请求级 ID | 无 | 入口生成/透传 traceId，放进 MDC，响应头回写 | 新增 `TraceIdFilter`（继承 `OncePerRequestFilter`） |
| 访问日志 | 无 | 每请求一条，含耗时和状态码 | 同上 Filter |
| 业务埋点 | 链上只有 `chain step` 文本 | 改成带字段的结构化事件 | `MenuHandlerChain`、各 Handler、`MenuTreeCacheService` |
| 单步耗时 | 无 | 每个 Handler 记录耗时 | `MenuHandlerChain` |
| 异常日志 | 已有 warn / error | 补 traceId 和错误码字段 | `GlobalExceptionHandler` |
| 指标 | 只暴露 `health` | 加 `prometheus` 端点，或直接从日志聚合 | `application.yaml` 的 `management` 段 |
| 容器权限 | 以 root 跑 | 建非 root 用户，日志目录 chown 给它 | `Dockerfile` |
| 采集与索引 | 无 | 加采集容器和索引端 | `docker-compose.yml` |
| 看板与告警 | 无 | 建仪表盘 + 阈值告警 | 检索平台侧 |
| 发布回滚 | 有流水线和健康检查 | 补一份"回滚到上一个镜像"的操作说明 | `.github/workflows/ci.yml`、`README.md` |

> ⚠️ **动手前先改一个坑**：`application.yaml` 里 `mybatis-plus.configuration.log-impl` 原来是 `StdOutImpl`，它绕过 logback 直接把 SQL 打到标准输出，既没有 traceId，又是日志量的黑洞。要改成 `org.apache.ibatis.logging.slf4j.Slf4jImpl`，并把级别降到 DEBUG，生产环境关掉。

每一行的技术背景，在[专题索引](#专题索引)里都有对应篇章。

### 关于汇丰（外部视角）

明确边界，避免把猜测当事实：

| 说法 | 把握程度 |
|:---|:---|
| 大型银行普遍要求请求级关联 ID、结构化日志、集中检索 | 高。这是行业通行做法 |
| 金融业大量使用 Splunk 这类集中日志平台 | 中。Splunk 在金融业很常见，但不是唯一选择 |
| 汇丰内部具体用什么平台、怎么分索引和权限 | 无。没有内部资料，不应替它下结论 |

> 🔑 **正确的讲法**：说"行业通用做法是 A、B、C，我在汇丰的项目里接触到的是其中的哪一部分"，而不是"汇丰就是这么干的"。

### 认知纠偏

| 误区 | 纠正 |
|:---|:---|
| "加了日志 = 有线上经验" | 日志只是链路的第 1 段，采集、索引、检索任何一段断了都白搭 |
| "用了 ELK 就比 Splunk 差" | 工具是次要的，**字段设计和检索能力**才是核心 |
| "日志当然越多越好" | 日志是成本。高频路径要分级或采样，否则索引量会失控 |
| "排查问题从读代码开始" | 从**指标和日志**开始，先定位到哪一层，再读代码 |
| "上线前测试充分就不会出事" | 变更本身才是最大风险源，所以要有灰度和回滚 |
| "Docker 就是跑应用的，不用管权限" | 容器是 Linux 进程，进程身份、文件属主都还是 Linux 权限模型在管 |
| "统一返回 200、错误码放 body 里更省事" | 省的是前端的事，代价是**监控瞎掉**：指标、告警、SLO 全建立在 HTTP 状态码上。系统异常必须 500，业务异常和参数错误给 4xx，body 的 `code` 只做细分 |

### 三个可以拿去讲的实战证据

| 证据 | 一句话讲法 |
|:---|:---|
| **200 骗指标** | 统一返回 200 时，指标写 `outcome="SUCCESS"` 而日志是 `ERROR`；改成状态码分类后，错误率才看得见 |
| **target 指着旧代码** | 8080 上跑的是旧镜像，没有 prometheus 端点，404 又被旧异常处理器包成 200 —— 看板全绿、用户全错 |
| **三个耗时窗口** | 同一次请求：访问日志 403ms、指标 410.6ms、curl 464ms，因为 filter 层层嵌套，越外面越大 |

## 🔥 面试要点

### 高频问题 + 标准答案

**Q1：线上接口变慢了，你怎么查？**

> **面试话术**：*"先看监控曲线，确认是全量慢还是个别接口慢、是突然劣化还是缓慢劣化。如果是个别接口，就用 traceId 拉一次慢请求的全链路日志，看耗时集中在哪一段，是数据库、下游调用还是应用自身。定位到层之后再看那一层的具体指标，比如慢 SQL、连接池等待、下游超时。"*

**Q2：你怎么知道服务现在是正常的？**

> **面试话术**：*"分三层。最浅的是健康检查端点，判断进程活着、依赖可达；中间是业务指标，比如接口成功率、P95 延迟、缓存命中率；最深是核心业务动作的成功率，比如菜单接口对每个分行都能返回。告警一般挂两个：5 分钟内 5xx 超过 1%，以及 P99 超过阈值。"*

**Q3：发布之后出问题怎么办？**

> **面试话术**：*"先止血。我们的镜像是按 commit 打的 tag，所以回滚就是切回上一个 tag 重启，几分钟内恢复。恢复之后再复盘，把发布前后的监控曲线对比，确认是不是这次变更引入的。所以流水线最后那步健康检查很关键，它是自动判断这次发布成不成功的关口。"*

**Q4：一个用户说他的菜单不对，怎么排查？**

> **面试话术**：*"菜单接口的日志里带了这个请求的全部维度：国家码、实体、渠道、网点、用户 ID。我用这几个字段去搜，就能看到这次请求走了哪几步、四维匹配命中了哪些配置、权限过滤砍掉了什么、最后有没有走缓存。如果缓存命中就是配置或缓存的问题，如果走了完整链路就看匹配和过滤的结果。"*

**Q5：日志量太大怎么办？**

> **面试话术**：*"分三层处理。第一是分级，DEBUG 级别的 SQL 日志只在开发环境开，生产关掉；第二是采样，超高频且低价值的事件按比例采样，但异常和慢请求必须全量；第三是保留周期，热数据留 7 到 30 天，更久的转冷存或直接过期。"*

**Q6：你遇到过最难的线上问题是什么？**

> 用 STAR 讲一个真实故事。没有一手故事，也必须准备一个"我参与过的排查"，并诚实说明自己在其中的角色。

### 项目里可以讲的排查剧本

没有真实事故可讲时，讲一个"线上真这样报，我会怎么处理"的推演，比空泛地说"我会看日志"有力得多。关键是三段齐全：**缩影响面 → 止血 → 定位 → 复盘**。

```java
① 现象 ── 看板显示 /api/menu/tree 的 P99 从 50ms 涨到 400ms
      │
      ▼
② 影响面 ── 只有上海分行，其他分行正常 → 影响面缩到"分行维度"
      │
      ▼
③ 止血 ──── 先看是不是这次变更引入：比对新发布 tag 的镜像和曲线拐点时间
      │          是 → 回滚上一个 tag；不是 → 继续定位
      ▼
④ 定位 ──── 按 branchCode=SH001 过滤，看 chain.step 的耗时分布
      │          发现卡在 LoadMenuHandler 的查库 → 捞出慢 SQL
      ▼
⑤ 复盘 ──── 为什么会慢：菜单配置行数涨了，匹配维度上缺索引
                 为什么没提前发现：告警只挂了错误率，没挂 P99
```

> 🔑 **这个剧本的价值在顺序**。只讲"我怎么查出根因"，暴露的是实验室调试思维；先缩影响面、再止血、最后定位，才是线上思维。面试官听的正是这个顺序。

> ⚠️ 讲的时候主动说明哪些是这个项目真做过的、哪些是推演。项目里已经有的：按提交打的镜像 tag（回滚的前提）、健康检查关口、`chain.step` 日志。只有采集链和看板告警是你要新搭的。

### 把外包经历讲成线上经验

外包候选人最容易被问倒的一句是"这些都是你自己做的吗"。**提前想清楚边界，主动说清楚，比被追问再解释体面得多。**

可以按这个顺序组织：

```java
先讲环境  →  "项目是汇丰的企业级系统，驻场开发，我负责后端其中一部分模块"
再讲动作  →  "我做过接口开发、联调、回归、发版支持和线上问题排查"
再讲证据  →  "发版有固定流程，出问题有固定的定位动作"
最后讲边界 →  "整体的可观测性平台由团队和运维维护，我是在这个平台上做排查"
```

> ⚠️ **不要模糊角色**。把团队的成果说成个人的，面试官追问两层就露了。**主动说明自己的位置，反而会让对方觉得你靠谱。**

同时，把"我当时看到过什么"变成证据：

| 你当时看到的现象 | 面试里可以说成 |
|:---|:---|
| 工单模板里有日志查询链接 | 团队有固定的排查入口，先看日志再看代码 |
| 报错信息里带一串 ID | 请求级关联 ID 是跨系统排查的基础 |
| 发版有检查单 | 变更管理是线上稳定的一部分 |
| 事故要写复盘 | 复盘是流程的一环，不是个人行为 |

## 🧠 记忆口诀

```
补线上经验，记四个字：看、准、快、回

  看 —— 有日志有指标有看板，流量和错误看得见
  准 —— 一个 traceId 串起全链路，能定位到具体那一次请求
  快 —— 止血优先于根因，回滚比排查快
  回 —— 每次变更都留退路，镜像是按提交打的 tag

再记两条红线：
  日志里不放敏感信息，定位靠 ID 不靠隐私
  容器里不用 root 跑应用，日志文件有明确属主
```
