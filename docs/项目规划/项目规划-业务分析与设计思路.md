## 一、业务背景：到底在干嘛

### 1.1 先搞清楚：这是一家什么公司的什么业务

这是一家**全球大型银行**，它在**30 多个国家和地区**都有业务。

每到一个新地方，银行会在当地注册一个或多个**法律实体**（Entity），这些实体是独立运作的业务主体。最常见的实体类型有：

| 实体类型 | 英文代号 | 做什么 |
|----------|----------|--------|
| 零售银行 | RETAIL | 给普通老百姓办储蓄卡、房贷、消费贷 |
| 私人银行 | PRIVATE | 给高净值客户（存款 100 万美金以上）做理财、信托 |
| 企业银行 | CORP | 给公司客户做对公账户、贸易融资、跨境结算 |
| 投资银行 | IB | 做 IPO、并购、股票债券承销 |

银行在不同国家有不同的实体组合。举例：

```
中国境内：  只有 RETAIL 和 CORP（中国不允许外资行做投行）
香港：      RETAIL + PRIVATE + CORP + IB（四大实体全有）
新加坡：    RETAIL + PRIVATE + CORP
百慕大：    PRIVATE + CORP（岛上主要是离岸业务）
```

每个实体下面可能还有**分行**（Branch），比如中国 RETAIL 实体下有：

```
上海分行 SH001
北京分行 BJ001
广州分行 GZ001
深圳分行 SZ001
...（共 30+ 分行）
```

### 1.2 再搞清楚：用户用什么渠道接触银行

用户和银行交互的方式叫「渠道」（Channel）：

| 渠道代号 | 渠道名称 | 典型用户 |
|----------|----------|----------|
| PC | PC 网上银行 | 上班族在电脑上转账理财 |
| APP | 手机 App | 所有人，随时随地查余额、转账 |
| ATM | ATM 自助机 | 取现、存款、打印流水 |
| COUNTER | 柜台系统 | 银行柜员在后台操作（给用户办卡、开账户） |
| CRM | 客户经理工作台 | 客户经理在后台看客户信息、卖产品 |

不同渠道的前端系统是**完全不同的项目**，由不同团队开发。

### 1.3 一个用户登录的具体场景

好，现在想象你是一个用户：

```
张三，上海人，在上海分行（SH001）开了一张储蓄卡
他属于：
  国家 = CN (中国)
  实体 = RETAIL (零售银行)
  分行 = SH001 (上海分行)

今天他打开手机 App（渠道 = APP）登录
登录后 App 首页左侧出现了导航菜单
```

这个导航菜单就是我们这个项目要管的东西。**张三看到什么菜单，取决于 4 个维度的组合**：

```
张三的菜单 = f(国家=CN, 实体=RETAIL, 渠道=APP, 分行=SH001)
```

如果换一个人：

```
李四，香港人，私人银行客户，在香港总行（HK001）
他打开 PC 网银：
  国家 = HK, 实体 = PRIVATE, 渠道 = PC, 分行 = HK001
  → 他看到的菜单 和 张三完全不同
```

### 1.4 这个菜单长什么样

我给你看一个真实的菜单树例子，张三（CN+RETAIL+APP）应该看到的：

```
首页
├── 我的账户
│   ├── 活期存款
│   ├── 定期存款
│   └── 外币账户
├── 转账汇款
│   ├── 行内转账
│   ├── 跨行转账
│   └── 跨境汇款
├── 理财投资
│   ├── 基金
│   ├── 理财产品
│   └── 股票（港股通）
├── 信用卡
│   ├── 我的卡
│   ├── 账单查询
│   └── 积分商城
├── 贷款
│   ├── 房贷
│   ├── 消费贷
│   └── 经营贷
└── 我的
    ├── 个人信息
    ├── 安全设置
    └── 帮助中心
```

而李四（HK+PRIVATE+PC）看到的是：

```
首页
├── 我的资产
│   ├── 投资组合
│   ├── 估值日报
│   └── 交易流水
├── 交易中心
│   ├── 股票交易
│   ├── 债券交易
│   ├── 基金申购
│   └── 外汇买卖
├── 财富管理
│   ├── 私募产品
│   ├── 信托计划
│   └── 保险规划
├── 客户经理
│   ├── 专属顾问
│   └── 预约会面
└── 设置
    ├── 开户地址变更
    └── 身份认证
```

可以看到差异非常大——**不同实体业务不一样，菜单完全不同；同一个实体，不同渠道展示的菜单数量和排序也不一样**。

## 二、旧系统现状：菜单是怎么管理的

### 2.1 前端硬编码 + if-else

在我们这个平台出现之前，菜单是这样管理的：

**每个前端渠道自己硬编码一套菜单。**

以 PC 网银前端项目为例，代码里直接写：

```javascript
// 这是 PC 网银前端项目 menu.js 里的代码（真实情况简化版）
const CN_RETAIL_MENU = [
  { id: 'home', name: '首页', path: '/home', children: [...] },
  { id: 'account', name: '我的账户', path: '/account', children: [...] },
  { id: 'transfer', name: '转账汇款', path: '/transfer', children: [...] },
  // ...
];

const HK_PRIVATE_MENU = [
  { id: 'home', name: '首页', path: '/home', children: [...] },
  { id: 'asset', name: '我的资产', path: '/asset', children: [...] },
  // ...
];

function getMenu(country, entity) {
  if (country === 'CN' && entity === 'RETAIL') return CN_RETAIL_MENU;
  if (country === 'HK' && entity === 'PRIVATE') return HK_PRIVATE_MENU;
  // ... 还有 20+ 个 if else
}
```

手机 App 的前端项目里也有一份**几乎一样但略有不同**的代码：

```java
// Android 项目里的 MenuConfig.java
public class MenuConfig {
    public static List<MenuItem> getMenu(String country, String entity) {
        // 和 PC 端差不多，但有些菜单名称不一样，有些菜单 App 上不展示
    }
}
```

柜台系统是第三份、CRM 是第四份……**同一套菜单逻辑被复制粘贴了 N 次**。

### 2.2 谁负责组树：旧系统 vs 新平台的关键架构差异

| 对比 | 旧系统 | 我们新平台 |
|------|--------|-----------|
| 组树在哪端 | 前端 | 后端 |
| 后端做什么 | 只查数据，不加工 | Fallback 匹配 + 权限过滤 + 递归组树，全部做完 |
| 前端要写组树代码？ | ✅ 每个前端都要写一遍 parent_id 递归 | ❌ 不用，拿到直接渲染 |
| 为什么旧系统让前端组树 | 2010 年只有 Swing 一个胖客户端，后端只服务一个调用方，谁组树都一样 | 要服务 N 个前端（PC/APP/ATM...），统一在后端做最省事 |

```
旧系统：
  后端 → 查数据库 → 返回平铺 JSON 数组（不加工，原样返回）
  前端 → 拿到平铺 JSON → 自己用 parent_id 递归组树 → 渲染

我们新平台：
  后端 → Fallback 匹配 → 权限过滤 → 自己递归组树 → 返回嵌套 JSON 树
  前端 → 拿到就是嵌套结构 → 直接渲染（不用自己组树）
```

**Legacy 兼容能成立的前提**：老系统接口返回平铺数组 → 我们后端必须自己组树 → 才能给新前端统一格式。

### 2.3 这样做有什么问题（5 个真实痛点）

#### 痛点 1：加一个菜单 = 改 N 个前端项目

业务部门说：「我们要给中国 RETAIL 加一个『数字人民币』菜单」。

- PC 网银前端 → 改代码 → 测试 → 发版
- 手机 App iOS → 改代码 → 测试 → 提交 App Store 审核（1-2 周）→ 发版
- 手机 App Android → 改代码 → 测试 → 提交各应用市场 → 发版
- 柜台系统 → 改代码 → 测试 → 发版
- CRM → 改代码 → 测试 → 发版

**加一个菜单，可能要协调 5 个不同团队，耗时 2-3 周。**

#### 痛点 2：同一个菜单，不同渠道名称不一致

- PC 端叫「转账汇款」
- App 端叫「我要转账」
- 柜台系统叫「资金划转」

产品经理每次看到都拍桌子，但没人愿意改——改了就要发版。

#### 痛点 3：权限逻辑藏在前端代码里

App 前端代码里：
```java
if (user.getPrivileges().contains("LUXURY_CARD")) {
    menu.add(new MenuItem("黑卡专区", "/luxury"));
}
```
现在业务说「我们要让金卡用户也能看到黑卡专区」——这得改前端代码、发版。而且**权限规则不应该由前端决定**。

#### 痛点 4：新国家/新实体从 0 开始搞

百慕大分行要开业了。没有现成的菜单可以参考（实体类型不同：PRIVATE + CORP），前端开发从零写菜单树，一周就过去了。

#### 痛点 5：Legacy 老分行完全不兼容

有 5 家老分行用的是 **15 年前的 Swing 胖客户端**。老系统菜单按「分行+岗位」配，新系统按「国家+实体+渠道+分行」配——两套体系完全不兼容。

## 三、核心流水线：串起整个系统的 5 步

### 3.1 一句话概括

> **请求进来先分流（Legacy / 新平台）→ 新平台内部：数据库散节点 → Fallback 按四维筛 → 权限再筛无权的 → 按 parent_id 递归组树 → 返回统一 JSON。**

### 3.2 完整流程图（含 Legacy 分流）

```
前端请求 {country, entity, channel, branch, userId}
    │
    ▼
┌────────────────────────────────────┐
│ ① Legacy 分流判断                    │
│                                      │
│  查 branch_config.use_legacy_menu    │
│  = 1 → 走老系统 → 格式转换 → 组树     │
│  = 0 → 走我们新平台的 ②③④⑤          │
│                                      │
│  本质：请求入口的第一道岔路口          │
└─────────────┬──────────────────────┘
              │
         ┌────┴────┐
         │         │
      = 1         = 0
         │         │
         ▼         ▼
┌──────────────┐   ┌────────────────────────────────────┐
│ 调老系统 API │   │ ② Fallback 全量匹配                 │
│ (分行+岗位)  │   │                                      │
│              │   │ 每条记录四维通配匹配                  │
│ 老系统返回的  │   │ 同一 node_id 多条匹配 → 保留最精确的  │
│ 平铺列表      │   │ 输出：属于这个用户的节点（平铺列表）   │
│ → 转换格式   │   └─────────────────┬──────────────────┘
│              │                     │
│              │                     ▼
│              │   ┌────────────────────────────────────┐
│              │   │ ③ 权限过滤                          │
│              │   │                                      │
│              │   │ 每条菜单 required_perm 裁剪           │
│              │   │ 父节点被砍，子节点一并砍掉            │
│              │   │ 输出：用户有权看的节点（平铺列表）     │
│              │   └─────────────────┬──────────────────┘
│              │                     │
│              │                     ▼
│              │   ┌────────────────────────────────────┐
│              │   │ ④ 构建菜单树                        │
│              │   │                                      │
│              │   │ 按 parent_id 递归串联                │
│              │   │ 按 sort_order 排序                  │
│              │   │ 输出：嵌套 JSON 树                   │
│              │   └─────────────────┬──────────────────┘
│              │                     │
│              └────────────┬────────┘
                           │
                           ▼
                   返回给前端渲染
```

### 3.3 各环节的输入输出

| 环节 | 输入 | 干的事 | 输出 |
|------|------|--------|------|
| ① Legacy 分流 | branch_code | 查 branch_config 开关 | 走老系统 or 走新平台 |
| ② Fallback 匹配 | 用户四维 (country+entity+channel+branch) + 数据库全部菜单 | 逐条通配匹配 + 精确优先去重 | 属于该用户的平铺节点列表 |
| ③ 权限过滤 | 上一步的列表 + 用户权限列表 | 按 required_perm 裁剪节点 | 无权的节点被砍，列表变短 |
| ④ 构建菜单树 | 上一步的列表 | 按 parent_id 递归串联 | 嵌套 JSON 树 |

**关键认知**：Fallback 和构建树是完全独立的两个环节。Fallback 只做筛选匹配，构建树只做结构组装。它们中间还隔着一个权限过滤。Legacy 分流是请求入口的第一道岔路口，与新平台内部的 Fallback/权限/组树并行。

### 3.4 上线前后对比

```
旧流程（上线前）：
  App 登录 → App 前端自己写死的 if-else → 直接渲染菜单 → 改了要发版

新流程（上线后）：
  App 登录 → App 调后端 Menu API → 带上 {country, entity, channel, userId}
  → Menu API：Fallback → 权限 → 组树 → 返回 JSON
  → App 拿到 JSON 渲染 → 改菜单直接改数据库配置，不用发版
```

## 四、设计原则：逐个环节展开

### 4.1 原则一：配置驱动，不是代码驱动

> 菜单 = 数据，写在数据库里。前端只是渲染器。

| 旧姿势 | 新姿势 |
|--------|--------|
| 前端开发改 JS 代码 | 运营/产品在后台改配置 |
| 提交 git → CI → 发版 | 保存数据库记录，立即生效 |
| 涉及 5 个渠道 × 5 个团队 | 只改一处 |
| 耗时：2-3 周 | 耗时：5 分钟 |

这是整个平台最根本的设计理念。

### 4.2 原则二：四维匹配，精确到人

> 一条菜单记录可以指定它对「哪个国家、哪个实体、哪个渠道、哪个分行」生效。

数据库里的一条记录：

| country_code | entity_code | channel_code | branch_code | node_name | node_path | parent_id | sort_order | is_active |
|-------------|------------|-------------|------------|-----------|-----------|-----------|-----------|-----------|
| CN | RETAIL | APP | SH001 | 数字人民币 | /digital-rmb | 100 | 5 | 1 |

（parent_id=100 表示挂在 id=100 的「我的账户」下）

这意味着「数字人民币」这个菜单**只对上海分行的中国零售银行 App 用户**可见。

如果想让它对所有中国零售银行的 App 用户可见，把 `branch_code` 改成 `*`（通配符）即可。

#### 插曲：先搞清楚 id、node_id、parent_id 三个字段

| 字段 | 是什么 | 唯一吗 | 用途 |
|------|--------|--------|------|
| **id** | 数据库自增主键，行号 | ✅ 每条记录唯一 | 数据库内部标识，不对外 |
| **node_id** | 业务层面的菜单项身份证号 | ❌ 可以重复 | **去重用**：同一个菜单项的不同版本（全局版/HK版...）共享同一个 node_id |
| **parent_id** | 指向父节点的 **id**（数据库主键） | — | **组树用**：构建 parent-child 层级关系 |

用实际数据看最清楚：

```
数据库里有两条记录：

id | node_id | node_name | country | parent_id
---|---------|-----------|---------|-----------
 3 | account | 我的账户   | *       | 0         ← 全局版（给除了 HK 以外的所有人）
 2 | account | 我的财富   | HK      | 0         ← HK 专属版（覆盖全局版给 HK 用户）

两条记录的关系：
  - id 不同（3 vs 2）：数据库认为它们是两行不同的数据
  - node_id 相同（都是 account）：业务上它们是「同一个菜单项的两个版本」
  - node_name 不同：给用户显示的名字不一样
  - parent_id 都是 0：两个版本都是根节点
```

**没有 node_id 会怎样？** 当 HK 用户同时匹配到这两条时，你只看到 id=2 和 id=3（两个不同的数字），你根本不知道这俩其实是同一个菜单项的两个版本——你会把两个都返回给用户，菜单里就出现两个「我的账户」了。

**Fallback 的精确优先去重就是靠 node_id 实现的**：node_id 相同 → 是同一个菜单项 → 去重只留最精确的那条。

### 4.3 原则三：全量匹配 + 精确优先去重（团队代号：Fallback）

> 数据库里每条菜单独立存在，运行时对每条做四维通配匹配；同一 `node_id` 有多条命中时，保留精确值维度最多的一条。

最终机制：

```text
1. 一次查询拉出全部有效菜单配置
2. 对每条记录逐维匹配：* 通配，具体值必须相等
3. 保留匹配成功的记录
4. 按 node_id 分组，精确值数量最多的版本胜出
```

这套方案用一次查询替代逐级 Fallback，不需要额外维护 level 标记，新增业务维度也不用改 SQL 次数。详细演进、真实数据例子和三组验证场景见 [业务架构-Fallback四维菜单匹配](../技术专题/业务架构/业务架构-Fallback四维菜单匹配.md)。

### 4.4 原则四：权限过滤在运行时，不在配置时

> 数据库里配置的是「所有可能存在的菜单」，用户能看到哪些，**运行时算**。

```
Step 1: 从 Fallback 拿到「CN+RETAIL+APP」这一级所有菜单（共 50 个节点）
Step 2: 查张三的权限列表：["LUXURY_CARD", "MORTGAGE", "FUND_INVEST"]
Step 3: 遍历 50 个菜单，看每个菜单的 required_perm
  → 普通菜单（首页、转账）：不需要权限，保留
  → 黑卡专区：需要 "LUXURY_CARD"，张三有，保留
  → 投资组合：需要 "PRIVATE_WEALTH"，张三没有，砍掉
Step 4: 砍掉父节点时，它的所有子节点一并砍掉（否则子节点没地方挂）
Step 5: 剩下 45 个节点 → 组树 → 返回
```

### 4.5 四条原则的关系

```
         ┌──── 原则一：配置驱动 ────┐
         │      （数据化，不发版）    │
         │                           │
原则二 ──┤                           ├── 原则四
四维匹配 │      原则三：全量匹配        │  权限过滤
（谁看） │      + 精确优先去重          │  （能看多少）
         │      （谁能看这条菜单）      │
         │                           │
         └───────────────────────────┘
```

## 五、Legacy 兼容方案（请求入口的分流开关）

> 每个分行可以独立选择「用新平台菜单」还是「用老系统菜单」，改一条数据库记录即可切换。这是请求进入后的**第一道判断**——在 Fallback/权限/组树之前。

### 5.1 背景：什么是 Legacy 老分行

```
2010 年：银行在香港有 5 家历史最久的分行（HK001、HK002...）
  → 用 Java Swing 写的 C/S 胖客户端（不是浏览器）
  → 菜单逻辑是 f(分行代码, 柜员岗位) —— 只有两个维度

2015-2020 年：新分行（上海、北京、新加坡、百慕大...）用新 Web 架构
  → 菜单逻辑是 f(国家, 实体, 渠道, 分行) —— 四个维度 + Fallback + 权限

2026 年的今天：
  → 95% 的分行在新架构上了
  → 那 5 家老分行还在跑 15 年前的 Swing 胖客户端
  → 老柜员平均 55+，没人敢动（香港利润最高的分行）
  → 老系统文档丢失，没人完全看得懂
```

### 5.2 老系统 vs 新平台的本质差异

| 对比点 | 老系统 Legacy | 我们新平台 |
|--------|--------------|-----------|
| 菜单分群维度 | `branch_code` + `staff_role`（2 个） | `country` + `entity` + `channel` + `branch`（4 个） |
| 有 parent_id 层级？ | ✅ 有，叫 `parent_menu_id` | ✅ 有，叫 `parent_id` |
| 有 Fallback？ | ❌ 没有 | ✅ 有 |
| 有运行时权限过滤？ | ❌ 没有 | ✅ 有 |
| 返回格式给外部 | 平铺 JSON 数组 | 嵌套 JSON 树 |

**关键发现：组树的底层原理完全一样——都是 parent_id 递归。所以能转换！**

### 5.4 代码路由（入口第一判断）

```java
public MenuTreeVO buildMenuTree(MenuQueryDTO dto) {
    // 第一步：先查这个分行的开关（请求入口第一判断）
    BranchConfig branch = branchConfigMapper.selectByBranchCode(dto.getBranchCode());
    
    // 第二步：开关开了 → 走老系统
    if (branch != null && branch.getUseLegacyMenu() == 1) {
        List<LegacyMenu> legacyMenus = legacyClient.queryLegacyMenu(
            dto.getBranchCode(),
            dto.getStaffRole()
        );
        return convertLegacyToNewFormat(legacyMenus);
    }
    
    // 第三步：开关关了 → 走我们的新平台逻辑
    List<MenuConfig> matched = fallbackService.match(
        dto.getCountry(), dto.getEntity(), dto.getChannel(), dto.getBranch()
    );
    List<MenuConfig> filtered = permissionFilter.filter(matched, dto.getUserId());
    List<MenuNodeVO> tree = treeBuilder.build(filtered);
    return new MenuTreeVO(tree, null);
}
```

## 七、发版机制：改菜单要不要发版？

### 7.1 不需要发版的场景（改数据库即可）

| 变更 | 操作 | 生效速度 |
|------|------|----------|
| 改菜单名称 | `UPDATE menu_config SET node_name = ?` | 缓存 TTL 到期后 / 主动删缓存后立即生效 |
| 改排序 | `UPDATE menu_config SET sort_order = ?` | 同上 |
| 新增菜单项 | `INSERT INTO menu_config ...` | 同上 |
| 删除菜单项 | `UPDATE menu_config SET is_deleted = 1` | 同上 |
| 改菜单层级（换父节点） | `UPDATE menu_config SET parent_id = ?` | 同上 |
| 改 Fallback 层级 | 改 country/entity/channel/branch 字段 | 同上 |
| 改某菜单需要的权限码 | `UPDATE menu_config SET required_perm = ?` | 同上 |

菜单节点名称来自数据库，代码里没有任何硬编码：

```java
// MenuFallbackService.java —— 核心匹配算法就是这样，不写死任何菜单内容
public List<MenuConfig> match(String country, String entity, String channel, String branch) {
    List<MenuConfig> allRecords = mapper.selectAllActive();
    List<MenuConfig> matched = new ArrayList<>();
    for (MenuConfig record : allRecords) {
        if (wildcardMatch(record.getCountry(), country)
            && wildcardMatch(record.getEntity(), entity)
            && wildcardMatch(record.getChannel(), channel)
            && wildcardMatch(record.getBranch(), branch)) {
            matched.add(record);
        }
    }
    return deduplicateByPrecision(matched);
}
```

加了 Redis 缓存：运营后台改完配置后主动 `cacheService.invalidateCache(id)`，下次请求缓存未命中，立即查数据库拿新值——不用发版。

### 7.2 什么情况才需要发版后端？

只有**规则本身变了**的时候：

| 场景 | 为什么要发版 |
|------|-------------|
| 新增 Fallback 维度（比如加「客户经理团队」） | `MenuFallbackService.java` 匹配算法要加一行判断 |
| 改权限过滤逻辑（比如支持「A 或 B」权限） | `PermissionFilter.java` 算法要改 |
| 数据库表结构变了（加新字段） | DDL + Entity + VO 都要改 |
| 新增渠道/实体枚举值 | `ChannelEnum.java` 要加新值 |

## 八、完整链路闭环回顾

> 最后，把整篇文档的知识点串成一个**故事链**，你应该能对着面试官流畅地讲出来——从痛点到方案到落地，一个完整的闭环。

```
① 为什么做（业务背景 + 旧系统痛点）
│   "全球银行 30+ 国家 × 4 实体 × 5 渠道 × N 分行
│    菜单散落在 5+ 前端硬编码，改一次 2-3 周
│    还有 5 家老分行系统完全不兼容"
│
② 怎么想的（设计原则）
│   "四条原则：配置驱动 / 四维匹配 / 全量匹配精确优先去重 / 运行时权限过滤
│    Legacy 不放在原则里，而是入口分流开关"
│
③ 怎么做的（核心流水线 5 步）
│   "请求进来 → ① Legacy 分流判断
│             → ② Fallback 全量匹配（通配符 + node_id 精确优先去重）
│             → ③ 权限运行时过滤
│             → ④ parent_id 递归组树
│             → 返回统一 JSON 树"
│
④ 怎么落地（实现策略）
│   "MySQL 存 menu_config + Redis 缓存
│    主接口 POST /api/menu/tree
│    代码分层：Controller → Service(Fallback/Permission/TreeBuilder) → Mapper"
│
⑤ 改了什么要发版（发版机制）
│   "90% 的变更（改名称/排序/权限）→ 改数据库 + 清缓存 → 不用发版
│    只有规则变了（加维度、改算法）→ 才要发版后端"
│
⑥ 老系统怎么迁（Legacy 迁移）
│   "branch_config 开关，改一条数据库记录切换
│    有问题立刻改回，风险可控，分行粒度迁移"
│
⑦ 带来什么价值（回到开头的痛点）
│   "改菜单从 2-3 周 → 5 分钟
│    新国家开业不用从零写菜单树
│    所有前端拿到统一格式，不用各自组树
│    老分行平滑过渡，不用一次性重写"
│
⑧ 面试怎么讲（一句话 + 追问）
    "配置驱动的多维度菜单聚合平台，把散落在前端的菜单收归后端统一管理"
```

**这就是闭环**：痛点 → 原则 → 方案 → 实现 → 发版 → 迁移 → 价值 → 面试，每个环节紧扣，每个环节的输出是下一个环节的输入。

## 九、总结：面试怎么讲

### 9.1 一句话

> <span style="color:red">**这是一个配置驱动的多维度菜单聚合平台，把散落在各前端硬编码的菜单收归后端统一管理，核心是「四维匹配 + 全量匹配精确优先去重 + 权限运行时过滤」。**</span>

### 9.2 三个面试高频追问

**Q：为什么要做这个平台？直接存 N 套菜单不行吗？**
A：旧系统把菜单硬编码在 5+ 个前端里，改一个菜单要协调 5 个团队耗 2-3 周。我们收归后端统一管理后，改菜单就是改一条数据库记录，运营自己就能操作，5 分钟生效。新国家开业也不用从零写菜单树，全局默认配好后插几条专属的就行。

**Q：Fallback 回退具体怎么做的？**
A：我们内部叫 Fallback，但实际上是**全量匹配 + 精确优先去重**——把所有菜单拉出来，for 循环对每条做通配匹配，`*` 通配任意值，精确值必须相等。同一个 node_id 有多条匹配时，保留精确值维度数最多的那条。比经典的逐级查询方案代码更简单，加新维度只要在循环里加一行判断就行，不用改 SQL 逻辑。

**Q：Legacy 老分行怎么兼容的？**
A：5 家香港老分行还在用 15 年前的 Swing 胖客户端，菜单只按「分行+岗位」两个维度配。我们做了**双轨并行**：`branch_config` 表加了 `use_legacy_menu` 开关，查询时先查这个开关——开关开就调老系统接口，然后把老系统的平铺菜单列表转换成我们统一的 JSON 树返回给前端；开关关就走 Fallback + 权限 + 组树逻辑。前端完全不用管后端走哪条路，拿到的 JSON 格式一致。迁移按分行粒度，改一条数据库记录就行，有问题立刻改回，风险可控。

### 9.3 核心关键词

| 关键词 | 对应什么 |
|--------|----------|
| 配置驱动 | 解决了「改菜单要发版」的痛点 |
| 四维匹配 | 国家 + 实体 + 渠道 + 分行 |
| 全量匹配 + 精确优先去重 | 团队内部代号 Fallback，替代经典逐级查询 |
| 运行时权限过滤 | 菜单结构与权限规则解耦 |
| Legacy 平滑迁移 | 分行粒度开关，双轨并行 |
| 后端统一组树 | 平铺 parent_id 列表 → 嵌套 JSON 树，前端零负担 |
